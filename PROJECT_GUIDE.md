# Admiral8 Renders

Единое руководство для ИИ-агента: создание и редактирование видео по запросу с помощью Blender, локальных инструментов и проверки результата. Отдельного приложения нет. AGENTS.md и README.md — только ссылки сюда. Сторонние лицензии и машиночитаемые каталоги остаются рядом с ресурсами и не являются дополнительными инструкциями.

## Начало работы

1. Прочитать [правила](#rules), [возможности и ТЗ](#spec), [подготовку](#setup). Определить текущую задачу по свежему запросу; локальный `out/workspace.json` указывает активную работу, её `project.json` содержит состояние и проверенные результаты. История чужого ролика не становится новым поручением.
2. Найти исходник через `py -3.11 tools/project_map.py`; для деталей использовать `--area render --symbols`, для пути — `--find contact --symbols`. Не читать весь код наугад. Карта не заменяет чтение изменяемого исходника и не обещает фиксированную экономию токенов.
3. Сверить требования с фактическими ресурсами, Git и инструментами. До постановки определить ориентиры качества по [общему стандарту](#quality-standard) и подходящим примерам. В project.json составить перечень применимых требований со ссылками на разделы этого руководства, способом проверки и статусом; не копировать туда полный набор правил. Перед выдачей сверить перечень с актуальным результатом: verified требует конкретного доказательства, not_tested не считается выполнением, неприменимость требует причины. При изменении сцены переоткрывать затронутые проверки. Это средство контроля пропусков, а не автоматическая гарантия художественного качества. Отметить необходимые проверки в `project.json`; неизвестные свойства не считать подтверждёнными.
4. После изменения проверить затронутый участок, стыки и итог. Перед показом выполнить художественную приёмку по правилам ниже. Обновить состояние, доказательства и следующий шаг; закрыть свои окна просмотра и захват.

## Структура и единые места хранения

| Объекты | Единственное основное место | Содержимое |
| --- | --- | --- |
| Правила, ТЗ, установка, накопленные уроки | `PROJECT_GUIDE.md` | Действующие инструкции без дневника производства |
| Исполняемые инструменты | `tools/`, корневые `video.*`, `scene*`, `dota_map.js` | Подготовка, рендер, звук, монтаж, проверки |
| Проверочные сценарии | `episodes/`, `scenes/`, `skits/`, `examples/` | Входы тестов и примеры форматов; не обещание универсальной автоматизации |
| Малые распространяемые ресурсы | `assets/`, `fonts/`, `vendor/` | Используемая графика и зависимости с лицензиями |
| Общая локальная библиотека | `cache/resources/` или `A8_RESOURCES` | Модели, декорации, программы, ИИ-веса, дополнения |
| Все пользовательские видеопримеры | `cache/resources/references/` | Нейтральные имена, `catalog.json`, хеши, происхождение и разборы |
| Извлечённые игровые данные | `_game/` | Подготовленные модели, анимации, звуки и каталоги Dota; результаты работ и проверок сюда не записывать |
| Работы и исходники видео | `out/<project>/` | Активные работы: `project.json`, исходники, сцены, рендеры, QA; учебные сцены — `out/study/`, сценарные сценки — `out/skits/`; не часть поставки |
| Архивы при завершении старых работ | `out/archive/` | Только проверенные архивы с RESTORE-MANIFEST; наличие проверять по локальному состоянию |
| Уникальные пользовательские вложения | `cache/resources/user-input/` | Нейтральные имена и каталог SHA-256; видеопримеры остаются в references |
| Тестовые результаты | `qa/`, `_fv_work/` | Воспроизводимые проверки и кэши, тестовые сценки — `qa/skits/`; не уникальные исходники |
| Каталог необязательных зависимостей | `docs/OPTIONAL_RESOURCES.json` | Версии, ссылки, хеши; не второй набор правил |

Не дублировать рабочие ресурсы в папках роликов без необходимости автономной упаковки сцены. Для каждого внешнего ресурса хранить источник, версию/дату, лицензию, контрольную сумму и назначение. Каталог отличает оригинал от производной копии и отсутствующего файла. Имена файлов и описания пользовательских примеров использовать с нейтральными идентификаторами без названий каналов. При переименовании обновлять ссылки и проверять сохранность содержимого; анонимизация названий не означает удаления водяных знаков или метаданных внутри медиа. При импорте сначала проверять SHA-256, чтобы не размножать одинаковые примеры. Примеры не идеальные эталоны: записывать удачные решения, недостатки и конкретные интервалы, применимые к задаче.

Исторические сцены и журналы не включать в чистую поставку. Проверочные копии релиза и их отчёты хранить внутри служебной папки проекта (`out/`), не создавать соседние датированные папки в `Projects` без отдельного запроса. Уникальные данные сохранять отдельно; удаление воспроизводимого мусора допускается после проверки назначения и зависимостей. Не переписывать Git-историю и не удалять неизвестные единственные копии. Уборка охватывает не только Git, но и локальные рабочие каталоги, известные внешние временные папки и серверные результаты Actions. Перед удалением отличать воспроизводимые кадры/кэши от исходников; уникальные старые работы сохранять один раз в проверенном архиве с картой восстановления, а не размножать резервные папки. После тестов удалять их воспроизводимые результаты, если они больше не нужны для текущей диагностики. `py -3.11 -B tools/workspace_hygiene.py` даёт аудит без удаления; внешние места проверять через повторяемый `--external`, не считать отсутствующий доступ доказательством чистоты. Исторический полный текст руководства доступен в истории Git; локальная резервная копия находится в `out/_history/`.

## Правила работы

### Правила проекта

Отвечать по-русски. Применять свежие уточнения пользователя и сохранять чужие изменения. Вопрос по ходу работы не считать остановкой задачи: кратко ответить и продолжать выполнение; приостанавливать работу по явной просьбе пользователя.

Ответственность распространяется на весь репозиторий: перед работой восстанавливать актуальный контекст по ТЗ, состоянию, документации и исходникам затрагиваемых компонентов; учитывать зависимости и последствия дальнейших изменений. Не требовать от пользователя повторять уже записанные требования. Статус документа не заменяет проверку фактических файлов, а работа над одной сценой не отменяет соблюдения общих требований проекта.

- Основной сценарий — пользователь передаёт ИИ-агенту ссылку на репозиторий и запрос на видео. Агент самостоятельно готовит окружение, ставит сцену в Blender, проверяет движение и звук, собирает MP4 и сохраняет исходники. Отдельное приложение, GUI, установщик и ZIP-запуск исключены из проекта; не восстанавливать их без нового явного запроса.
- Сначала проверить исходник и зависимости. Для сцены проверить общий силуэт, геометрию, контакты, свет и звук дешёвыми пробами. После изменения окружения проверить каждый используемый ракурс на перекрытие камеры геометрией; выборка крупных планов не покрывает общие планы. При новой серии сначала проверять окружение каждого точного ракурса отдельной пробой без героя и глубины резкости, до чистового рендера и показа подборки. Обрывы карты, чёрные силуэты недостроенной геометрии и незаполненный дальний план блокируют кадр; исправить геометрию или выбрать цельный участок. Не повторять проверенный дефект в серии и не считать его скрытие героем или размытием исправлением. Один GPU-рендер за раз. Независимые части большой задачи (например, аудит кода, проверку GitHub и художественный разбор) поручать доступным агентам параллельно с явно разделёнными файлами и ответственностью; основной агент проверяет и объединяет результаты. Не распараллеливать зависимые правки одной сцены или конкурирующие GPU-рендеры. Для рук и реквизита проверять реальный контакт и деформацию с двух сторон.
- После изменения сверять запрос с фактическим кадром, движением и звуком. Техническая проверка не подтверждает художественную оценку. Перед показом сверить каждый существенный пункт промпта и последующие уточнения с фактическим кадром или отрезком, затем посмотреть результат глазами зрителя: куда смотрят герои, где стоят, что задевают и как реагируют. Самостоятельно исправлять обнаруженные расхождения до выдачи, чтобы пользователь оценивал художественный выбор, а не выявлял очевидные ошибки за агента. Выполненный чек-лист и успешный рендер не оправдывают заметное нарушение здравого смысла. В подвижном плане проверить весь рискованный момент в рабочем темпе, включая то, что происходит между выбранными кадрами. Если при собственном просмотре виден брак, исправить его причину и повторно проверить тот же кадр или отрезок. До чистового рендера проверить самые рискованные планы и переходы. Выдавать результат как готовый только после этой проверки. Если пользователь просит показать работу раньше, назвать её пробой и явно указать заметные незакрытые дефекты. Фиксировать границы проверки в текущем состоянии проекта.
- После правок кода запускать быстрые и целевые проверки из [карты инструментов](#tools). Проверки, использующие общую блокировку или выходную папку, выполнять последовательно. [подготовка](#setup) описывает работу агента в новом окружении. Перед коммитом просматривать diff, добавлять только относящиеся к задаче файлы. Автор коммита — `Codex <codex@openai.com>`.
- Использовать бесплатные локальные средства. Проверять версии, происхождение и лицензии новых зависимостей. Публикация, расходы и необратимое удаление уникальных данных требуют разрешения.
- Перед загрузкой крупных моделей и серийным рендером проверять запас места для самих файлов, временной распаковки и кадров. После переполнения диска проверять целостность созданных медиа; существование файла не подтверждает успешную запись. Уникальные сцены не удалять ради освобождения места.
- После проверки закрывать открытые для неё проигрыватели и завершать сеанс захвата экрана. Перед служебным запуском Dota или другого приложения фиксировать исходное состояние изменяемых настроек, включая сохраняемые переменные, режим окна и интерфейс. После захвата восстанавливать зафиксированные значения, останавливать запись и закрывать только свой экземпляр приложения; проверять завершение процесса и сеанса захвата. Не подменять исходные значения настройками по умолчанию; если исходное состояние не сохранено, явно отмечать предел проверки. Если жёлтая рамка Windows остаётся, проверить завершение процесса захвата; закрытие проигрывателя само по себе не подтверждает остановку захвата. Перед передачей старой папки на удаление проверять оставшиеся агентские процессы: даже простаивающий REPL может удерживать её как рабочий каталог. Завершать только подтверждённые собственные процессы и повторно проверять освобождение папки. Чужие окна и фоновые рендеры не закрывать.
- В Git хранить код, необходимые ресурсы, короткую инструкцию и актуальное ТЗ. Файлы Dota, веса моделей, отчёты, ключи, временные файлы и готовые ролики держать локально. Медиа в чате показывать абсолютным путём. Локальный путь доступен на исходном ПК.

#### Постоянные критерии качества
Критерии действуют для следующих работ, а не только для сцены, где обнаружена ошибка. Принятые пользователем образцы из `out/workspace.json` задают исходный уровень качества. До показа сравнивать с ними результат, а не переносить настройки вслепую; исключённые и отклонённые работы не использовать как ориентиры. Другой художественный характер допустим по замыслу, но не оправдывает технические или постановочные дефекты.

Существенные замечания переводить в проверяемые общие правила по [порядку обновления](#state), уточняя существующий пункт вместо дубля. Конкретные кадры, таймкоды, принятие и нерешённые дефекты хранить в `project.json`. После принятия или просьбы остановить полировку не добавлять новые улучшения без запроса.

Ниже — критерии по темам. [Свет и цвет](#quality-light), [камера и глубина резкости](#quality-camera), [контакты](#quality-contacts), [ресурсы и окружение](#quality-assets).

##### Проверка результата и границы работы

- Перед изменением читать применимые требования и состояние работы; новое замечание переоткрывает затронутую приёмку. Перед показом видео просмотреть полный монтаж в рабочем темпе: смысл, композицию, темп, движение, деформации, контакты, материалы, свет/мерцание и звук. Детали проверять в исходном масштабе и размере телефона. Выборка кадров не подтверждает отсутствие ошибок между ними; статичные кадры не подтверждают движение или звук. Фиксировать метод, охват, находки, исправления и ограничения. Успешный рендер и технические тесты не заменяют художественную оценку. Исправить заметные дефекты и повторить затронутые проверки и стыки, не расширяя задачу новыми идеями.

- До дорогого общего рендера собрать короткие проверки всех рискованных узлов в один проход: хват и одежда, выпуск предмета, реакция на попадание, падение и покой, свет и эффекты. Повторные локальные исправления без проверки целой последовательности затягивают работу и возвращают уже устранённые дефекты. После просьбы закончить не расширять объём новыми улучшениями; довести согласованный проход до полного файла. Оценивать срок по измеренной скорости и оставшимся кадрам, отдельно учитывать сборку и просмотр.

- Технический способ выполнения и проверки выбирать самостоятельно по результату, не ждать от пользователя предложения открыть приложение или сменить инструмент. Если скрипты и отдельные пробы повторно пропускают визуальную ошибку, менять способ диагностики: осматривать сцену интерактивно, изолировать проблемную геометрию, проверять несколько ракурсов и непрерывное движение. Открытое приложение и выполненный расчёт сами по себе не подтверждают качество результата.

- Для возобновления рендера сохранять хеш сцены, настройки и происхождение кадров. Повторно использовать кадры только после проверки, что изменения не влияют на их геометрию, материалы, свет, камеры и эффекты; существование PNG не подтверждает целостность. После паузы продолжать с проверенных недостающих кадров, затем проверять полный MP4 и стыки. Принятую пользователем версию и закрытие задачи фиксировать явно; согласие оставить результат не означает поручения запускать ещё один рендер.

- Проверять передачу работы новому агенту: README, правила и настройка должны приводить от запроса к запрошенному результату и редактируемым исходникам без отдельного приложения и скрытого контекста предыдущего чата. Не подменять запрос готовым примером. Указывать необходимые локальные ресурсы и фактические ограничения инструментов.

- Учитывать устройство просмотра: локальная ссылка на ПК не доставляет материал пользователю на телефоне. Для удалённого просмотра передавать сам файл доступным способом; загрузку, доступ и воспроизведение проверять раздельно. Не просить оценивать недоступный материал.

- Выходные пути Blender и других внешних инструментов задавать абсолютными. Проверять файл именно по ожидаемому пути, журнал выполнения и manifest: завершение процесса само по себе не подтверждает успешное создание результата.

##### Постановка, смысл и монтаж

- Перед пародией на известную сцену установить участников, смысл происходящего и причинную последовательность по референсу и при необходимости первоисточнику. Переносить в Dota роли, намерения, реакции и ключевой монтаж. Не подменять узнаваемую сцену произвольной шуткой по внешнему сходству кадра. До показа сверить смысл и последовательность с исходным фрагментом.

- Образное сходство с персонажем референса не означает буквальную замену цвета кожи или игрового облика. Согласованные изменения силуэта и характера переносить на узнаваемую модель героя. Сохранять смысловую географию действия (лестницу, высоту наблюдателя, препятствия), проверять опоры архитектуры. Для слышимой речи ставить артикуляцию по реплике и её времени, отдельно проверяя рот в крупных планах и опору стоп на каждой ступени.

- При разборе пользовательских референсов отделять наблюдаемый приём от предположения о технологии и от случайного дефекта. Для короткой постановки заранее определять понятный вход, изменение ситуации и завершающую реакцию; крупности и движения камеры выбирать под смысл, а не ради разнообразия. Разбор текущей подборки — [PROJECT_GUIDE.md#references](#references).

- Живость персонажа проверять по вниманию, выражению лица, согласованию головы/корпуса/рук и реакции на партнёра. Для узнаваемой игровой способности заранее проверять наличие и постановку её оригинального эффекта, а не считать физическое последствие заменой визуалу способности. Не заменять эмоциональную постановку непрерывной ходьбой, тряской или одинаковой активностью всей группы. Намеренный гротеск и масштабный контраст должны читаться как замысел и не оправдывают случайные дефекты контакта и анатомии.

- Фоновое событие не превращать в самостоятельный эпизод без сюжетной необходимости: не отдавать ему отдельный крупный план, громкий звуковой акцент или реакцию героев, отвлекающие от основного действия.

- До чистового рендера смотреть черновой монтаж целиком в рабочем темпе. В цепочке действий сначала показать исходное положение предмета и намерение героя, затем контакт и видимое последствие. Проверить, что без звука понятно, кто действует, на что и что изменилось. Если это теряется на склейке или за эффектом, переставить действие или камеру и повторить проверку. Тряска камеры должна быть мотивирована событием и затухать после него; в финальном плане реакции не оставлять остаточное дрожание или рывки. Проверять конец ролика в рабочем темпе отдельно от ударов и спецэффектов.

- Для главного перехода размечать начало подготовки, атаку звукового эффекта, визуальную кульминацию и появление результата в секундах и кадрах. Сверять с референсом и дорожкой; одиночная вспышка на склейке не заменяет содержательное изменение окружения. Отдельно фиксировать просмотр референса, анализ тайминга и фактическое прослушивание — не выдавать одно за другое.

- На склейке сохранять смысловой ориентир, если действие связано с препятствием или раскрытием героя из-за него. Проверять пару кадров до/после и переход в рабочем темпе: крупный читаемый герой не компенсирует исчезновение колонны, двери или другого сюжетно важного объекта. В наплыве отдельно проверить кадры наложения: двойные лица и силуэты не должны закрывать ключевой взгляд или жест. Если в это время происходит важное действие, сместить границу перехода или выбрать склейку.

- При переносе сцены в другое пространство согласовывать фон, освещение, отражения и исчезновение окружения. Качественный фон сам по себе не подтверждает качество перехода: проверять масштаб деталей, границы масок и мерцание при движении камеры. Одинаковые точки и широкая неоновая обводка не заменяют художественную постановку космоса.

<a id="quality-assets"></a>

##### Ресурсы, масштаб и целостность окружения

- Перед сравнением с примерами проверять комплектность импортированной карты: воду и её материал, берега, склоны и дальний план. Экспорт геометрии не гарантирует переноса игровых шейдеров; служебное скрытие поверхности не должно незаметно убирать содержательную часть окружения. Цвет и детализацию фона оценивать отдельно от героя. Проверять самую даль через просветы между стволами и декорациями, а не только верхнюю линию неба: карта не должна заканчиваться видимой пустотой. Для каждого видео выбирать содержательный дальний план по месту и жанру. Открытое небо, море, степь или намеренная пустота допустимы по замыслу; случайный обрыв карты и необъяснимые просветы до фона — нет. В лесу продолжать растительность несколькими пространственными слоями, включая нижний ярус между стволами; не закрывать отдельную дыру сплошной каменной стеной. Не заменять подлесок уменьшенными взрослыми деревьями и не заполнять просветы плотными рядами копий. Сохранять природный масштаб, интервалы и ясную композицию; добавленная даль должна восприниматься как продолжение места, а не склад декораций. Один ряд деревьев, размытие или затемнение не заменяют проработанную глубину. Проверять края дальнего плана в начале и конце каждого движения камеры, включая широкие ракурсы.

- Для персонажей, противников, карты, растительности, разрушений, архитектуры, оружия, реквизита и техники выбирать качественные совместимые исходники. Для узнаваемого игрового предмета сначала искать оригинал; при отсутствии подобрать или изготовить модель с читаемой конструкцией и поверхностью. Рекламное «realistic», размер файла, число полигонов, увеличение текстуры или подразделение сетки сами по себе не доказывают детализацию. До рендера сверять LOD, геометрию, реальные размеры карт, UV, нормали и маски; крупный план проверять отдельно. Сравнивать весь ресурс с героями при общем свете: силуэт, конструктивные детали, стекло, металл, ткань, дерево и износ. Примитивный или игрушечный предмет заменять, а не скрывать затемнением. Замена сетки требует проверки рига и всей анимации. Не допускать разрыва качества между героями, предметами и окружением.

- При смене героя или сцены заново проверять кожу, металл, ткань, лицо и фон в целевом ракурсе. Материалы и постобработку сравнивать на одинаковых позе и камере, с разрешёнными пользователем ориентирами. При ухудшении определить причину и повторить сравнение; пути кадров, вывод и нерешённые дефекты сохранить в `project.json`.

- При совмещении отдельно импортированных героев и карты сверять единицы и коэффициенты масштаба до постановки. Не нормализовать разных героев к одинаковому росту: сверять исходные размеры, игровой ModelScale и общий перевод единиц, затем проверять соотношение силуэтов в совместном кадре; художественное отклонение должно быть осознанным. Уменьшение героев без согласованного изменения окружения недопустимо. Проверять рост относительно дороги, растительности и архитектуры в общем плане; после изменения масштаба повторно проверять опору ног, препятствия и все камеры.

- Видимую полосу или «дыру» сначала диагностировать: отдельно проверить геометрию, нормали, материал и свет. Граница освещения может выглядеть как шов; отсутствие геометрического отверстия не означает приемлемый кадр. При расхождении вьюпорта, ray cast и рендера сверять видимость объектов и коллекций в обоих режимах: скрытые во вьюпорте служебные меши карты могут оставаться видимыми в рендере. Не принимать чёрные заглушки за плохое освещение леса и не скрывать нужные поверхности только из-за флага вьюпорта. После удаления заглушки заново проверить заполненность фона во всех рабочих планах: показавшееся небо или край карты не считать восстановленным окружением. Соседние поверхности пола сверять по реальной высоте и фаскам, архитектурные элементы — по видимой опоре и назначению. Согласовывать износ собственных моделей с игровыми ресурсами, не пытаться исправить несогласованную форму одной текстурой.

- Проверку контактов с окружением проводить с видимым окружением: скрытая колонна или стена делает такую пробу непригодной для приёмки. Для опоры учитывать все видимые поверхности пола, включая вспомогательные покрытия и заполнение разрывов карты: контакт с исходным рельефом не исключает погружение под добавленную поверхность. До общего рендера изменённого действия просмотреть короткую последовательность с рабочей камеры и проблемный контакт с двух сторон. Отсутствие пересечений сеток не подтверждает читаемый зазор в кадре.

- Рябь на стыке объектов проверять на дублирующиеся и совпадающие поверхности (z-fighting). Устранять перекрывающиеся грани или объединять геометрию; увеличение сэмплов не исправляет конфликт глубины.

- Для узнаваемого элемента Dota сначала искать исходную модель, текстуры, анимацию, эффект и звук в установленной игре. Если оригинал доступен, использовать его, а не самодельный аналог. Извлечение отдельных текстур не считать переносом всей системы частиц: при неподдерживаемых операторах проверить воспроизведение в исходном движке и перенос отрендеренного слоя. Явно различать оригинальный ресурс, запись из движка и авторскую реконструкцию. Для способностей проверять ссылки на ресурсы в игровом описании эффекта. Сохранять узнаваемый силуэт, цвет и движение. При замене эффекта сохранять его смысловую основу: дым, пламя и разряды не должны подменять или полностью скрывать ядро сферы. Проверять основу и окружающие частицы вместе в масштабе телефона. Избегать произвольных сфер, декоративных точек и экранных колец вместо существующих игровых эффектов.

<a id="quality-contacts"></a>

##### Анатомия, хват и опора

- После изменения пропорций персонажа повторно проверять стык головы и туловища, включая открытый рот и повороты. Закрывать щели геометрией с правильными весами и текстурой; маска, тень и ракурс не считаются исправлением. Сначала установить фактическую открытую кромку сетки и поверхность соединения, не подменять их приблизительной вставкой. Для поднятой маски проверить физический контакт с волосами/лбом с двух сторон; положение выше лица само по себе не подтверждает посадку. Посадку носимого предмета сверять с анатомическими ориентирами, а кадрирование — с полным силуэтом предмета и его движением.

- После усиления мимики или наклона головы проверять бороду, волосы, воротник и наплечники относительно груди на всей реакции, включая открытый рот и возврат в позу. Проверять фактическое направление движения рига в мировых координатах; название оси и знак поворота не доказывают отклонение назад. Для длинной бороды согласовать её отдельную кость с движением головы и инерцией.

- Сначала проверить конструкцию предмета, крепление рукояток и позу всего героя; не подгонять руку под ошибочную геометрию. Решать плечо, локоть, предплечье, запястье и пальцы как одну цепь. После перемещения локтя не сохранять автоматически прежнюю мировую ориентацию кисти: это может скрутить предплечье. Предмет опирается на поверхность ладони, пальцы естественно обхватывают его; совпадение точек хвата, оружейной кости или успешный IK этого не доказывает.

- Проверять полный силуэт и весь предмет спереди, сбоку и сзади, крупно — запястье, ладонь, пальцы и манжеты, затем всю дугу действия с рабочей камеры: касание, удержание, смену хвата, выпуск, отход и возврат. Проверять проход оружия относительно предплечья, корпуса и окружения; допустимое касание пальцев не путать с проникновением в торс. Любое изменение стойки, корпуса, плеч, локтей или оружия отменяет прежнюю проверку хвата, даже если численные координаты пальцев совпали. Отсутствие пересечения сеток не гарантирует читаемый контакт в кадре.

- Если повторные исправления хвата ухудшают позу, сохранить отклонённую версию и пересобрать движение от проверенной исходной позы рига. Не наследовать накопленные компенсирующие повороты. Сначала проверить всю цепь плечо–локоть–кисть и деформацию сетки, затем посадку предмета; подтвердить результат короткой последовательностью с двух сторон и в рабочей камере.

- При создании или удержании предмета двумя руками проверять его положение относительно обеих ладоней на каждом кадре удержания. Для перехвата отдельно проверять рабочий ракурс: направление движения, оружие, точка касания и реакция должны читаться раздельно. Совпадение точек в 3D не подтверждает понятную постановку.

<a id="quality-motion"></a>

##### Движение, реакции и тайминг

- Для 3D использовать управляемый риг и FK/IK по задаче. При изменении скорости исходной анимации интерполировать дробное время (позиции и масштаб — плавно, вращения — quaternion/slerp), не округлять его до целых исходных кадров; иначе движение дублирует позы и становится ступенчатым. Проверять скорость кистей и корпуса на всех последовательных кадрах изменённого участка, затем в рабочем темпе. Перенос движения на другой риг требует проверки пропорций, осей, костей и контактов. У составной модели сначала определить основной скелет по телу и полной цепочке костей, затем проверить связи скелетов аксессуаров. Не выбирать управляющий риг по порядку объектов; после замены движения убедиться, что тело и все детали следуют новой анимации, а старые действия не продолжают управлять отдельными частями. Мимика, взгляд, дыхание и вторичные движения должны поддерживать намерение, а не добавлять случайный шум. Наличие мимики проверять по shape keys в сцене и targets/accessors исходного glTF, а не только по extras.targetNames: отсутствие этого необязательного поля не доказывает отсутствие морфов. Сначала задействовать доступные исходные морфы, затем искать новый инструмент.

- При вращении падения учитывать смещение скелета относительно origin объекта: сохранять траекторию таза и повторно проверять опору, положение героя и камеру. Скорость экшена сверять по прохождению ориентиров карты, частоте и длине шага и движению камеры; синхронное сопровождение может скрывать ускорение. При ощущении плоскости отдельно проверять силуэт на фоне, направление света, ракурс, перенос веса и последствия удара; начинать с короткого законченного фрагмента, а не перекрашивать весь фильм.

- Скорость модели проверять вместе с пройденным расстоянием, масштабом сцены, FPS и характером усилия. Падение должно ускоряться и завершаться понятным контактом; растягивание траектории на длительность ролика не оправдывает зависание или слоумо. Фоновое событие может закончиться раньше ролика. Проверять весь видимый отрезок при целевых FPS и переход к покою.

- При замене анимации после ретайминга проверять старые дробные ключи и движение на долях кадра: ровные целочисленные позы не исключают рывков и смаза между ними. Удалять ключи обратным индексным проходом, затем проверять фактическое отсутствие конфликтующих ключей и повторять пробу с motion blur.

- Не обнулять скорость на каждой промежуточной позе и не строить движение как очередь изолированных жестов. Сохранять раздельные смысловые контакты, но позволять взгляду и переносу веса готовить следующее действие, а руке и корпусу продолжать движение после усилия. Уверенность выражать опорой, ясным намерением и работой плеч, а не случайной тряской. Проверять переходы в рабочем темпе: без непреднамеренных пауз и наложения кульминаций. Если действиям тесно, менять длительность и монтаж, сохраняя естественную скорость замаха, броска и реакции.

- Использовать игровые анимации только там, где они подходят действию. Для нестандартного жеста, стрельбы из другого оружия, броска, реакции на взрыв и продолжения действия ставить собственную анимацию; не склеивать неподходящие игровые клипы. Проверять подготовку, действие, последствия и выход из него в рабочем темпе. Не возвращать героя в нейтральный idle сразу после напряжённого события.

- Не подменять отдачу сильной тряской персонажа. Проверять вместе скелет, одежду, манжеты и отдельные навесные детали по всей последовательности; отлетающий рукав или рывок аксессуара считается браком даже при совпадении ладоней с оружием. Скорость монтажа должна оставлять время прочитать контакт и последствие.

- Замечание о спешке исправлять локальным таймингом подготовки и контактов, не замедлением всей сцены. Для проверки боевой анимации сохранять целевой FPS проекта; разреженный рендер не подтверждает плавность. После ретайминга проверять фазу шага, скорость продвижения и непрерывность вращений на каждом стыке.

- Для падений и взрывов анимировать направленную реакцию на конкретное событие, контакт с рельефом и окончательную остановку. Разделять импульс, полёт, первый контакт с землёй и затухание; одно плавное вращение целого тела не заменяет передачу веса и индивидуальную реакцию. При падении сохранять длины и объём скелетных цепей: не заменять вращение суставов независимым переносом костей или их масштабированием. Согласовывать траекторию центра массы, потерю опоры, захват и остановку тела; попадание кисти в цель не оправдывает растяжение руки. Проверять ускорение и рывок от захвата в рабочем темпе, включая переходы до и после падения. Не заменять их одинаковыми клипами смерти, перемещением целого тела по дуге или вспышкой без столкновения. Проверять пересечения транспорта, роторов и тел с картой до общего рендера.

- Для неорганизованной толпы избегать одинаковых дистанций, ровных рядов и синхронных циклов. Различать направления, скорости, фазы шага и реакции на препятствия; проверять общий план и движение целиком. В намеренно синхронном групповом номере проверять, читаются ли общий рисунок и ведущий герой на общих акцентах. Перед наложением частиц проверить групповую сцену без них, включая различимость фигур, опору и зазоры в крайних позах. Напряжение боевой сцены выражать осмысленными действиями героев — перемещением, переносом веса, укрытием, взглядом и реакцией на угрозу, а не только эффектами и тряской камеры.

<a id="quality-materials"></a>

##### Материалы и диагностика шейдеров

- При подготовке материалов сохранять исходные карты металличности, шероховатости и прозрачности. При чёрных треугольниках на импортированной модели отличать дефект текстуры от освещения и геометрии пробой с неизменённым Base Color без освещения; проверять согласованность обхода полигонов и пользовательских нормалей. Исправлять подтверждённую причину с сохранением UV и фактуры, не закрашивать артефакт.

- Ошибка маски кожи не оправдывает одинаковую матовость всех материалов героя. Проверять, что импортированные карты действительно участвуют в нужных входах материала и используют содержательный канал: наличие specmask с непрозрачным alpha не означает работающую маску бликов. Авторскую адаптацию игровых масок в PBR отличать от точного воспроизведения исходного шейдера; оценивать её вместе со светом на одинаковых ракурсах. Исправления задавать адресно и проверять отдельно кожу, металл, ткань и вырезы волос. Для любых объектов, включая реквизит и окружение, проверять соответствие блеска материалу на поворотах и в движении камеры: резкое белое пятно на металле не считать допустимым лишь потому, что кожа уже исправлена. Сверять тёмные материалы с оригинальными ресурсами: волосы, борода и ткань не должны становиться равномерно серыми из-за заливки или отражений; при снижении бликов сохранять детали, объём и различия материалов.

<a id="quality-light"></a>

##### Свет и цвет

- Проверять относительную яркость героя, реквизита и фона: сохранять смысловую иерархию, но не терять форму важного предмета в тени; при необходимости добавлять локальное заполнение, не осветляя и не обесцвечивая весь кадр.

- Свет и материалы принимать на всём движении при рабочем FPS, включая смену ракурсов, повороты, раскрытие суставов и крайние позы; статичные пробы не закрывают эту проверку. До дорогой сборки использовать короткий проход всего движения: проверять скачки яркости и экспозиции, выбитые светлые участки, сохранение деталей в тенях, оттенки кожи, металла и тёмных материалов. Подозрительный момент разбирать на всех последовательных кадрах до и после события; отличать освещение и отражения от деформации, видимой изнанки геометрии, денойзинга и композитинга. Исправлять установленную причину и повторять тот же интервал плюс весь монтаж; естественный блик сам по себе не является ошибкой. В project.json сохранять метод, охват и конкретные наблюдения проверки света, а не только отметку о просмотре отдельных кадров.

- Согласованное дневное направление для Dota-сцен: чистый достаточно насыщенный цвет, естественная тёплая земля, мягкие блики и детали в светах, без белёсости, серого налёта, жирного глянца или кислотной травы. Приглушённую оливково-болотную обработку пользователь отклонил. Другой свет и палитра допустимы по конкретному замыслу; не возвращать отклонённые варианты автоматически.

- Оттенок, насыщенность и тональный диапазон настраивать раздельно. Оценивать героя, землю и листву отдельно и вместе: яркий костюм не оправдывает перенасыщенный фон, а большая серая дорожка может делать весь кадр тусклым. Снижение насыщенности не устраняет бирюзовый сдвиг. Сначала проверить исходную текстуру, множители, активные старые поправки, тональное преобразование и нейтральность света; не складывать унаследованную надбавку насыщенности с новой постобработкой автоматически. Не исправлять серость общей зелёной или жёлтой заливкой.

- Корректировать материал адресно, сохраняя фактуру и цветовые различия. Проверять белые поверхности, цветную ткань, тёмные материалы, ближнюю/дальнюю землю и листву при их фактическом свете. Если ствол и крона используют общий атлас, отделять коррекцию листьев маской. У соседних частей земли с общими слоями согласовывать цветовые множители и проверять стыки без героя/DOF: резкий цветовой зигзаг по границе полигонов остаётся дефектом, даже если перекрыт персонажем.

- Слишком контрастный фон исправлять балансом направленного и заполняющего света и яркостью материалов. Не поднимать общую экспозицию ради фона, обесцвечивая героя; при необходимости восстанавливать детали локальным заполнением. Туман и дымка требуют основания в замысле и не заменяют мягкий свет или оптическое размытие. После правки проверять сохранение согласованной погоды и прозрачности воздуха.

- При переносе сцены сохранять и проверять систему света и фактический состав получателей каждого источника: свет плаща или реквизита не распространять на всего героя. Замена камеры или удаление источника не должна возвращать тёмный фон. Независимо проверять ветки видимого неба и освещения мира. У перемещённых декораций проверять шейдерные привязки к мировым координатам: подводная тонировка и другие эффекты высоты не должны окрашивать сухую сцену. После цветовой правки повторить те же планы; мерцание оценивать на последовательности при рабочем FPS.

<a id="quality-camera"></a>

##### Камера, фокус и глубина резкости

- Сохранять предпочитаемые пользователем ритм и акценты. Проверять заметное оптическое отделение фона на каждом ракурсе, включая общие планы и кадры после склеек; один размытый портрет не закрывает всю серию. Смена дистанции, фокусного расстояния или крупности требует новой проверки: одинаковая диафрагма не сохраняет глубину резкости.

- Фокусировать на поверхности лица/глазах конкретного героя, учитывать важные руки и реквизит, опору и читаемость силуэта. Общая высота для всех героев и центр кости не заменяют проверку резкости. При намеренном переводе резкости внутри плана заранее определить, кто удерживает внимание, что запускает перевод и кому оно переходит. Проверять исходную и конечную резкость, читаемость цели за передним планом и время на реакцию после перевода. Не заставлять фокус следовать каждому жесту и раскачивать неподвижный фон. Если крупная ветвь или скала находится в той же фокальной плоскости, увеличить расстояние до неё или изменить постановку, затем заново проверить фон и опору. Не добиваться размытия декораций ценой нечитаемых лица и ног. Если теряются вытянутые руки, сначала согласовать плоскость фокуса, глубину действия и дистанцию до фона.

- Различать мягкость света, глубину резкости, смаз и потери разрешения/перекодирования; общее замыливание не заменяет DOF. Очередной монтаж собирать из исходных кадров, а не из цепочки пережатых версий. Краткий эффект смотреть вместе с кадрами до/после; смешивание с негативом может дать серый провал вместо вспышки.

<a id="quality-effects"></a>

##### Эффекты и передача предметов

- Захваченные из игры последовательности эффектов проверять целиком на постороннюю геометрию, выделение и интерфейс; наличие оригинального источника не гарантирует чистый слой. Удалять постороннее адресной маской, сохраняя сам эффект, и повторно проверять всю используемую последовательность.

- У физического взрыва отдельно проверять видимую форму частиц: не оставлять одинаковые кубы или другие заметные примитивы вместо обломков. Согласовывать сколы с материалом поверхности, варьировать форму и размер. Проверять весь разлёт и столкновения: отскок и вращение затухают, частицы не продолжают крутиться на зажатой высоте. Такой дефект исправлять до показа, а не оправдывать условностью эффекта.

- Ключевой эффект или реквизит должен читаться на экране телефона. Проверять крупность в рабочем кадре и усиливать масштаб в смысловой кульминации, сохраняя видимость героя и точки контакта. Для орбитальных сфер и других движущихся эффектов проверять всю траекторию относительно головы, корпуса, рук и одежды, включая кадры между опорными позами. Оригинальность ресурса не подтверждает правильность его размещения: ядро и видимая оболочка не должны проходить сквозь героя или непреднамеренно прижиматься к лицу. Задавать читаемый зазор с учётом полного размера эффекта; подтверждать его и в 3D, и в рабочем ракурсе при целевом темпе.

- Проверять переходы между удержанием, перехватом и свободным движением эффекта. Пока его держат, положение следует за обеими ладонями или точкой удержания реквизита; не завершать привязку раньше видимого перехвата. После отпускания направление и скорость продолжают действие. Показывать подход, касание и начало переноса непрерывным планом; проверить весь интервал удержания и проход предмета мимо обоих героев, покадрово и в рабочем темпе, включая склейки. Отдельная красивая траектория не должна выглядеть самостоятельным полётом.

<a id="quality-audio"></a>

##### Звук и надписи

- Звук автоматического оружия должен иметь читаемые атаки, плотную очередь и прекращение огня; короткий периодически повторённый срез и постоянные синусоидальные тоны могут превращать его в гул. Проверять оружие отдельно и в сведении. Отклонённые голосовые пробы не переносить в следующий ролик; узнаваемость не выводить из имени модели или игрового референса.

- Для голосов персонажей сверять русские игровые источники и узнаваемость отдельно от разборчивости. Звуки окружения и действий должны соответствовать месту и событию. При наличии субтитров выдерживать один стиль во всём ролике. Авторские надписи оценивать отдельно по формулировке, типографике, размеру на телефоне и времени чтения. Замечание о визуальном стиле текста не считать просьбой переписать его содержание. Короткий текст должен поддерживать заход или событие, не дублировать очевидное действие и не мешать мимической реакции. Проверять титры в итоговом кодированном видео; правки текста выполнять на стадии сборки без ненужного пересчёта 3D.

<a id="quality-render"></a>

##### Рендер, композитинг и экспорт

- Перед серийным финалом проверять рискованные широкие планы при итоговом разрешении: дешёвый черновик не выявляет переполнение буфера теней EEVEE. Контролировать предупреждения Shadow buffer full, увеличивать ёмкость в пределах VRAM и пересчитывать весь затронутый план. Увеличение разрешения само по себе не подтверждает сохранность теней.

- При экспорте sRGB PNG явно задавать согласованные матрицу RGB→YUV, диапазон и метаданные: tools/media_color.py используется Blender-экспортом и браузерным PNG-кодировщиком. Одни теги без преобразования матрицы могут исказить цвет. Проверять реальный encode/decode на светлых, тёмных и цветных образцах; это не заменяет художественную цветокоррекцию или проверку конкретного телефона. Этот путь не предназначен для произвольного HDR-видео.

- При ряби проверять не только сэмплы и денойзер, но и композитинг, маски глубины, прозрачность и объёмы. Сравнивать один кадр до/после композитинга, затем последовательность. Не использовать несглаженную глубину как финальную маску на дыме, листве и motion blur без визуальной проверки. При раздельной сборке героя и фона сохранять перекрытие землёй и другими объектами: скрытие окружения для камеры не должно раскрывать подземные части модели. Проверять alpha/holdout на прозрачной листве, границах силуэта и опорах, чтобы не возникали чёрные точки, ореолы или висящие над полом предметы. У импортированных декораций проверять не только собственную анимацию объекта, но и управляющие скелеты, модификаторы и унаследованные действия. Не накладывать полную статическую модель на её игровую анимированную версию роста или разрушения. Сравнивать геометрию без размытия и проверять начало ролика отдельно: стабильность выборки из середины не доказывает стабильность всей последовательности.

<a id="spec"></a>

## Техническое задание и границы возможностей

### Назначение и ответственность

Агент самостоятельно ведёт техническую часть: анализирует запрос, сценарий, ресурсы и ограничения; подбирает средства; создаёт сцену, анимацию, камеры, свет, эффекты, звук, субтитры и монтаж; выдаёт проверенный запрошенный результат — MP4 для видео или изображения для статичной задачи — и редактируемые исходники. Обычные технические решения не перекладывать на пользователя. Выявлять конкретные препятствия качеству и исправлять их в пределах задачи, не превращая разработку в бесконечное расширение функций.

Поддерживать 3D, 2D/motion graphics и их сочетания: персонажные истории, диалоги, комедию, экшен, трейлеры, музыкальные, образовательные и информационные ролики. Стиль, тип анимации, рендерер, формат, разрешение, FPS, продолжительность, уровень качества и способ автоматизации независимы. Вертикальный формат не означает упрощённое 3D. Целевые пропорции: 9:16, 16:9, 1:1, 4:5 и другие по задаче; FPS 24/25/30/60 и другие корректные значения; разрешение до 4K и выше по возможностям оборудования. Для длинных работ использовать планы и возобновляемый монтаж, а не один непрозрачный расчёт.

**Фактическая граница:** произвольный художественный запрос выполняет агент средствами Blender/API/CLI. `quickstart.py` и локальный планировщик поддерживают ограниченные схемы и правки; они не являются автономной моделью, способной без постановки создать любое видео. Новую возможность считать реализованной только после реального результата, а не создания JSON-плана. Уровни Preview / Production / Maximum и Manual / Assisted / Automated описывают выбранный процесс; доступность конкретной комбинации проверять на используемом инструменте.

### От запроса к результату

Извлечь идею, жанр, участников и роли, действия, окружение, стиль, настроение, длительность, формат, разрешение, FPS, язык, реплики, звук и ограничения. Использовать разумные значения по умолчанию; уточнять только существенно влияющее на результат. Зафиксировать сценарий, планы, причинную последовательность действий, камеры, свет, список ресурсов, анимационные и звуковые события, монтажные границы и критерии приёмки.

Сначала проверять доступность и качество ресурсов. Если их нет, оценить исходники игры, законные библиотеки, адаптацию, ретаргетинг, процедурную генерацию или подходящую локальную модель. Простые геометрические заменители не выдавать за готовые детализированные модели. Для промптовых правок сохранять исходный запрос, диапазон и зависимости: изменение реплики не должно пересчитывать независимую геометрию; изменение позы требует повторной проверки контактов.

Рабочее описание должно содержать версию схемы, запрос, сценарий, сцены, актёров, ресурсы, камеры, свет, анимации, реплики, эффекты, звук, субтитры, таймлайн, режим качества и экспорт. Существующие схемы задания рендера, монтажного проекта и 2D-сцен не объединять формально в несовместимый универсальный объект: `project.json` связывает их путями. Проверять данные до передачи инструменту. Временная шкала использует целые кадры и точные отношения частот; звук размечается в сэмплах без накопления округления.

### Архитектура и надёжность

Предпочитать поддерживаемый модульный проект вместо сервера, GUI или микросервисов без необходимости. Логические области: проекты/запросы, сценарии, ресурсы, сцены/анимация, камера/свет, аудио/субтитры, монтаж, рендер, QA и экспорт. Границы определяются реальными зависимостями; не создавать отдельный сервис для каждой области.

Каждое долгое задание имеет входы, промежуточные файлы, manifest, блокировку, логи и проверяемое завершение. Запись атомарная, кэш идентифицируется хешами входов и настроек. После прерывания переиспользовать только проверенные кадры. Отсутствие свободного места, повреждённый кадр, смена сцены/рендерера, ошибка кодировщика и конфликт параллельных запусков должны давать понятную ошибку без порчи исходника. Одновременно не запускать конкурирующие GPU-рендеры.

Не сохранять абсолютные пути конкретного компьютера в переносимом коде. Пути к программам и библиотекам задаются через существующие `paths.py` и `resource_paths.py`, параметры CLI и переменные окружения. В manifest локальной работы абсолютные пути допустимы, если явно обозначены как локальные.

### Качество анимации и изображения

До постановки составлять в `project.json` конкретные критерии по применимым направлениям: смысл, актёрская игра, камеры, движение/контакты, ресурсы/окружение, материалы, свет/цвет/глубина, эффекты, звук, экспорт, сравнения и оформление. Для каждого указать наблюдаемый результат, способ проверки и подходящий пример; неприменимость объяснить. Хорошее лицо на фоне сырой карты не выполняет общий уровень качества.

Подробные критерии находятся в [постоянных правилах](#quality-workflow), работа с примерами — в [разделе референсов](#references), доказательства — в [состоянии работы](#state). Сравнивать уже первые пробы до дорогого рендера и итог перед выдачей. Исправлять конкретную причину отставания; разрешение, насыщенность, число эффектов и установленных дополнений не заменяют выразительность и целостность. Палитру, частоту склеек и активность выбирать по замыслу.

### Звук, речь, субтитры и монтаж

Диалоги, музыка, атмосфера и эффекты идут отдельными дорожками. Использовать подходящие EQ, компрессию и автоматизацию громкости, контролировать клиппинг и True Peak. Выбирать TTS по языку, произношению, интонации, эмоциям, стабильности, лицензии и RAM/VRAM. Русский и английский обязательны как направления поддержки; наличие конкретного голоса не предполагать. Крики и неречевые эмоции оценивать отдельно от обычной речи.

Липсинк связывает фонемы/висемы, forced alignment, кривые рига и выражение лица. ASR-разметка не подтверждает точность на слух. Субтитры: корректные тайминги, ручная правка, языки, шрифты, переносы, единый стиль и безопасные зоны; word-level использовать только при достаточной точности. Графика и монтаж поддерживают смысл, эмоциональный ритм и музыкальные акценты, а не количество переходов.

### Авторский стиль и подпись

Предлагаемый визуальный почерк подтверждать реальными пробами из рабочего конвейера на оригинальных ресурсах: материалами, светом, композитингом и движением. Сгенерированная иллюстрация не доказывает достижимый вид ролика и не заменяет такой пример. До одобрения не объявлять пробную обработку утверждённым стилем и не применять её ко всем новым видео.

Данные автора хранятся в `assets/creator/brand.json`: точный регистр ника и юзернейм сохранять. Общий модуль `tools/creator_brand.py` использует лицензированные шрифты проекта и создаёт титры и отдельный слой утверждённого логотипа; способ смешивания и непрозрачность брать из конфигурации. Для титров использовать спокойный современный гротеск средней насыщенности (исходно Manrope 600), светлый однотонный текст и небольшую тень без толстой обводки, разноцветных акцентов и игровых плашек. Текст не обязателен: понятный визуальный гэг не снабжать поясняющими титрами. Утверждённый логотип не менять вместе со стилем титров; он остаётся плоским, без обводки. В примерах изучать принципы читаемости, иерархии и размещения; не воспроизводить чужую плашку или знак.

Оформление должно быть ненавязчивым: маленький логотип «AdmiraL 8» в безопасном углу; юзернейм не выводить. Знак — тяжёлая современная рубленая надпись с крупным якорем вместо i; лапы якоря направлены вверх, низ угловатый, без нижнего острия-стрелки. Буквы согласовывать с геометрией якоря, избегать округлой пузырчатой и рукописной формы. Не оформлять знак как спортивную нашивку: без университетских засечек, толстой цветной обводки и рельефа; использовать чистые плоские формы. Цветовое направление — морская палитра Кунки; конкретный вариант проверять в небольшом размере поверх видео. Узнаваемость развивать последовательностью титров, монтажных акцентов и подачи, без обязательной длинной заставки, громкой звуковой метки и крупного водяного знака. Подпись и титры не должны перекрывать лица, руки, реквизит или кульминацию. Предпочтительное размещение логотипа — снизу слева с отступом; исходная непрозрачность 38%, корректируемая по читаемости. Проверять графику на всём ролике и в размере телефона; если угол занят, корректировать размещение под сцену. Цвета авторской графики не задают единственную цветокоррекцию и освещение для всех роликов. Начальный и финальный текст оформлять согласованно; не удерживать подпись-сообщение поверх реакции только ради постоянного присутствия текста.

Экспорт слоя логотипа: `py -3.11 -B tools/creator_brand.py --width 720 --height 1280 --out out/<project>/renders/brand.png`. Команда не перезаписывает существующий файл. Слой имеет чёрную подложку для смешивания `screen`, а не готовую прозрачность RGBA: обычный `overlay` покажет чёрный прямоугольник. Режим и непрозрачность берутся из `brand.json`; сохранять RGB до единственного преобразования диапазона при финальном кодировании. Ширина логотипа задаётся долей короткой стороны кадра; на другом соотношении сторон проверять размещение отдельно. Быстрый вход к ресурсам — `tools/project_map.py --area branding`.

### Внешние улучшения

Для конкретного ограничения исследовать первичные источники: официальные документации и релизы, GitHub, Hugging Face и воспроизводимые исследования. Направления включают Blender/Cycles/Eevee/Geometry Nodes, glTF/USD, FFmpeg/монтаж/композитинг, локальные LLM/TTS/ASR, генерацию текстур и ресурсов, ретаргетинг, липсинк, анализ и тестирование. Это список направлений, а не обязательных установок.

До интеграции записать: решаемую проблему, альтернативы, ожидаемую пользу, версию и источник, лицензию, размер, RAM/VRAM, зависимости, разрешения, сетевые/файловые операции, способ установки, отключения и проверки. Проверять исходники исполняемого кода; безопасный формат весов не гарантирует безопасность загрузчика. `trust_remote_code` без проверки не использовать. Не запускать неизвестные установочные скрипты, не захламлять глобальное окружение и не подключать внешние аккаунты без согласия.

Стабильный выпуск с фиксированным хешем предпочтительнее плавающей ветки. MCP нужен только когда даёт преимущество перед доступным API/CLI; не устанавливать его ради наличия. Проверять минимальные разрешения, ограничение файлов, секреты, отключение и диагностику. Бесплатная локальная работа — основной режим; расходы, публикация, доступы и существенные изменения ОС требуют согласия. Возможность, которая только установлена, отличается от проверенной на конкретной задаче.

### Проверки и критерии готовности

Базовый набор: unit, integration, smoke/end-to-end, проверка восстановления, кэша, таймлайна, ресурсов, рендера, кодирования, звука и визуального результата. Для релиза проверять чистую копию без старых работ и локальных игровых данных, установку зависимостей и реальные MP4. CPU-проверки отделять от GPU и художественной приёмки.

Целевые сценарии приёмки: кинематографичные 3D 9:16 и 16:9, 2D Shorts, смешанный контент, адаптация формата, создание по запросу, правка по запросу, восстановление. Пока сценарий не проверен, не считать его готовым. Проверка MP4 включает полное декодирование, потоки, FPS, размер, длительность, число кадров, timestamps, неожиданные пустые/зависшие кадры, окончание звука и синхронизацию. После текста и других накладок сравнивать декодированные кадры MP4 с исходными PNG вне области накладок: совпадение цветовых тегов не доказывает сохранение цвета. При RGB-источниках сохранять RGB на стадии overlay (например, format=rgb), затем один раз преобразовывать диапазон и матрицу в выходной YUV; повторное сжатие диапазона после неявной конвертации делает изображение выцветшим. Художественная приёмка описана в правилах и не заменяется тестом. Для полного технического прохода готового файла: `py -3.11 -B tools/reference_review.py PATH.mp4 --id neutral-id --out out/WORK/qa/technical-new --technical-only`. Команда декодирует первые видео- и аудиодорожки целиком, сохраняет SHA-256, число кадров, интервалы black/freeze, LUFS/True Peak, версию и журналы FFmpeg. Нулевой код FFmpeg и progress=end сами по себе не доказывают полноту: проверять сообщения о преждевременном EOF/повреждении и заявленное число кадров; расхождение длительности контейнера рассматривать отдельно, учитывая хвосты дорожек. Чёрный кадр или остановка — повод для проверки, а не автоматический дефект; отсутствие срабатываний не доказывает качество анимации, контактов, звука или синхронизации. Проверки художественного результата и прослушивания остаются отдельными. Обычный режим этого же инструмента делает только выборку кадров.

Измерять подготовку, первый кадр, рендер/кодирование, RAM/VRAM, размер кэша и повторную сборку. Применять инстансинг, разумные текстуры/геометрию/LOD, кэширование, инкрементальный рендер, CPU fallback и квантизацию ИИ по необходимости. Не снижать качество незаметно под видом оптимизации.

Релиз готов в проверенных границах, когда структура понятна, зависимости управляемы, основные сценарии работают из чистой копии, известные критические ошибки устранены, инструкции соответствуют коду и сохранены доказательства. Не объявлять проект идеальным, поддержку любых роликов — универсальной, а рекламные ускорения — измеренными.

## Состояние работ, замечания и продолжение

В поставке нет активного пользовательского ролика. Локальный `out/workspace.json` хранит указатель на работу; `out/<project>/project.json` — статус, актуальные входы/выходы, решения, замечания, проверки с доказательствами, нерешённые дефекты и следующий шаг. Исторические результаты не переносятся в новый проект как текущие поручения.

Каждое существенное замечание: (1) записать фактическую проблему и интервал/объект, (2) установить причину, (3) переформулировать в применимое требование, (4) найти существующее правило и уточнить его вместо дубля, (5) добавить способ проверки, (6) применить к текущему результату. Предпочтение конкретного ролика остаётся в его состоянии; универсальный урок — здесь. Не записывать каждый комментарий как бессрочный глобальный запрет. Прямое «не сохраняй» пользователя соблюдать.

Перед работой и выдачей агент сверяется с относящимися разделами руководства; отметки о проверках содержат фактический метод и границы. Использовать статусы implemented, tested, verified, not_tested, blocked, experimental по смыслу: наличие кода, запуск проверки и подтверждение результата различаются. Отчёт кратко сообщает результат, важные изменения, доказательства и оставшиеся ограничения. Не обещать память вне сохранённых файлов.

Новая работа создаётся через `py -3.11 -B tools/project_workspace.py <name> --prompt "<запрос>"`: инструмент заранее добавляет незавершённые направления проверки из общего стандарта. До постановки заполнить конкретные критерии под запрос и выполнить `py -3.11 -B tools/review_gate.py out/<project>/project.json --stage plan`. Успешная проверка плана подтверждает наличие записей, а не качество сценария. До дорогого рендера проверить черновой монтаж, все рискованные действия и каждую склейку; после него отдельно проверить итоговый MP4. Начало и конец каждого плана проверять на скачки трансформации камеры, цели слежения, фокуса и переключения камер: техническое дёрганье не списывать на художественную тряску.

Для готового видео отметку `ready_for_user_review` ставить только через `py -3.11 -B tools/review_gate.py out/<project>/project.json --mark-ready`, после художественной проверки; вручную присваивать `ready_for_user_review` нельзя. Без флага команда только проверяет записи. Непройденный допуск означает незавершённую приёмку: не выдавать файл как проверенный финал. Если пользователь явно просит текущий материал или оставляет известный дефект, показать его с указанным ограничением и сохранить статус `retained_with_known_limits`, а не обходить проверку и не продолжать ненужные исправления.

Для статичных кадров и серий сохранять критерии, фактическую визуальную проверку, пути и хеши изображений/сцен, ограничения и решение пользователя. `--stage plan` применим к плану, но текущий `--mark-ready` требует видео и не является допуском для изображений: не выдумывать видеопоток, движение или прослушивание. Статус статичной работы указывать отдельно, например `stills_ready_for_user_assessment` или `accepted_static_series`.

Схема проверки готового видео в `project.json`:
- `requirements` покрывает направления `story`, `acting`, `camera`, `motion_contacts`, `assets_environment`, `materials`, `light_color_depth`, `effects`, `audio`, `export`, `references`, `branding`. Это индексы к критериям руководства, не второй набор художественных правил. В одном направлении допускается несколько конкретных требований. Каждый пункт содержит уникальный `id`, `domain`, `source` вида `PROJECT_GUIDE.md#quality-standard` и конкретный `criterion`. Неприменимость: `status: not_applicable` и содержательная `reason`; отсутствие речи само по себе не делает неприменимой проверку звуков действий.
- Проверенный пункт имеет `status: verified`, фактический `method`, `evidence_files: [{"path":"qa/review.json","sha256":"..."}]` и `revision: {"video":"<SHA-256>","source":"<SHA-256>"}` именно проверенной версии. Пути относительны папке работы. Дополнительные исходники и зависимости перечислять в отчёте сборки.
- `review` содержит хеш текущего руководства `guide_sha256`, время с часовым поясом `reviewed_at`, объяснение применимости `coverage_note` и `artifacts` с относительным путём, SHA-256 и уникальной ролью; обязательны `video` и `source` (сцена/авторский вход).
- `review.observations.motion` содержит `mode: continuous_full_speed`, `revision`, фактическую `note` и `evidence` с путём/хешем отчёта. Этот режим означает реально проверенное непрерывное движение всего монтажа при целевом темпе. Серия снимков работающего плеера остаётся `sampled`, даже если плеер прошёл весь ролик; она не закрывает этот допуск. `review.observations.audio` имеет ту же структуру с `mode: listened` после фактического прослушивания или `no_audio_stream` при подтверждённом отсутствии звуковой дорожки. Метрики громкости не заменяют прослушивание. При недоступной возможности оставить проверку незавершённой и прямо назвать ограничение.
- `review.defects` явно содержит найденные дефекты с описанием и статусом. `open` и `user_waived` блокируют художественную готовность; отказ от исправления сохраняется с точным решением пользователя и позволяет закончить работу с ограничениями. `verified_fixed` требует описания, текущей `revision` и `evidence`. Пустой список допустим после проверки, а не как способ скрыть замечание.

Изменение руководства, видео, сцены или доказательства требует проверить актуальность технического допуска: инструмент сверяет хеши. Переоткрывать затронутые критерии и документировать, какие доказательства можно перенести; не обновлять хеши механически ради прохождения. Редакционная правка руководства сама по себе не отменяет пользовательское принятие результата и не требует нового рендера. Пересмотр содержания требований и изменение результата оценивать отдельно. Инструмент проверяет покрытие направлений, структуру и актуальность записей, но не способен доказать правдивость оценки или гарантировать отсутствие визуальных ошибок. Ответственность за прочтение всех применимых правил и честную оценку остаётся у агента; независимый разбор использовать для сложных и ранее пропущенных дефектов.

## Работа с видеопримерами

Для наработки качества начинать с видео, которые предоставил или одобрил пользователь. Разбирать конкретный приём в исходном видео и сохранять таймкод и наблюдение: что делает герой, как это показывает камера и почему приём читается. Собственную пробу использовать для применения и сравнения с исходным видео. Отклонённые работы годятся только для диагностики их ошибок. В руководство переносить только применимый к другим сценам вывод.

Канонический каталог — `cache/resources/references/catalog.json` (или путь под `A8_RESOURCES`); правила именования и происхождения — в разделе хранения. Использовать накопленный разбор библиотеки и выбирать под задачу несколько подходящих, не исключённых пользователем примеров. Не пересматривать автоматически всю подборку при каждом запуске; недостающий аспект проверять по исходнику, новые примеры включать в общий разбор.

Для постановки движения или монтажа смотреть выбранный фрагмент целиком в обычном темпе, отдельно изучать ключевые контакты и склейки; звук фактически прослушивать, если вывод касается звука. Для статичной задачи по цвету, материалам или композиции допустимы точные кадры с указанными таймкодами и границами проверки. Контактный лист не подтверждает просмотр движения, а метрики — прослушивание.

Вести перечень охваченных примеров, сверять производные кадры с хешем исходного видео, различать оригиналы, копии и отсутствующие материалы. Фиксировать интервалы, композицию, силуэт, вес/скорость, реакции, свет/цвет, эффекты и звук в пределах реально выполненного просмотра. Для недостатка указывать кадр/таймкод, подходящее сравнение и наблюдаемый критерий исправления. По возможности сравнивать одинаковых героев и близкие планы: другой костюм, свет или ракурс не доказывает превосходство LOD или текстуры.

Отделять наблюдаемый приём от предположения о технологии и случайного дефекта. Примеры не безупречны и не задают один стиль. Сравнивать конкретный приём, не копировать всё видео и не усреднять цвет разнородной подборки. Для числовой цветовой цели выбирать совместимые примеры: `py -3.11 tools/skit/grade.py target example-A1.mp4`; результат — `grade-target.json`, автоматический выбор всего каталога отключён. Для короткого развлекательного ролика проверять заход, ожидаемое действие, кульминацию и реакцию; комедия не обязательна для других жанров. Реклама инструмента не доказывает его автономность, скорость или качество на текущем риге.

## Подготовка окружения и работа

### Работа с репозиторием через ИИ-агента

#### Начало новой работы

Выполнить [входной порядок](#начало-работы) и определить ресурсы для текущего запроса. Проверить установленность Blender, Python и FFmpeg/ffprobe; для Dota — игры и Source2Viewer. До загрузок и рендера проверить версии, доступную память, GPU и место. Использовать имеющиеся инструменты прежде установки новых. Рабочую папку создать следующей командой; постановочные пробы и приёмку выполнять по [критериям качества](#quality-workflow).

#### Создание рабочей папки

`py -3.11 tools/project_workspace.py my-video --prompt "Описание видео"` создаёт `out/my-video/` с `project.json` и папками source, scenes, audio, renders, qa. Команда не генерирует видео и не перезаписывает существующую работу. Сценарий и постановку агент готовит после чтения запроса. Для внешней папки использовать `--parent`.

#### Интерактивное управление открытым Blender

Для серии правок и осмотра одной открытой сцены доступен проверенный MCP for Blender 2.2.9 (MIT). Установка: `py -3.11 -B tools/blender_bridge.py install`; пакет и Windows/Python 3.11 зависимости закреплены хешами в OPTIONAL_RESOURCES. Используется отдельное локальное окружение; глобальные настройки не меняются. Обычные фоновые сборки и финальный рендер остаются на Blender Python API.

Запускать собственный GUI-процесс: `blender.exe scene.blend -P tools/blender/interactive_bridge.py`. Затем из корня проекта: `py -3.11 -B tools/blender_bridge.py call get_scene_info --output out/WORK/qa/info-new`. Для изображения: `call look --args-file PATH.json --output out/WORK/qa/look-new`, где JSON, например, `{"mode":"camera","shading":"solid","max_size":640}`. Для адресной правки: `call execute_blender_code --script PATH.py --output out/WORK/qa/edit-new`; код предварительно прочитать, последствия проверить. Каждый результат сохранять в новой QA-папке. Это официальный MCP SDK, работает из текущего чата без регистрации нового сервера и перезапуска Codex. Команда `config` только печатает необязательную конфигурацию, сама ничего не подключает.

Проверены изменение объекта, анимация, изображения, а также read-only осмотр Dota-сцены с 4373 мешами. Solid view пригоден для поз, геометрии и ракурсов; material view использует студийный свет и может неправильно отображать native FX. Он не заменяет Cycles-рендер и просмотр всего движения. Замеры на одной сцене не обещают такую же скорость на любых сценах.

Мост включается только явно, слушает `127.0.0.1:19876`; автозапуск, телеметрия и проверка обновлений отключены, пользовательские настройки не сохраняются. У socket нет аутентификации, safe mode не является sandbox: не открывать порт наружу, не выполнять непроверенный код. Отключение — `bpy.ops.blendermcp.stop_server()` или закрытие собственного процесса Blender; после работы проверить закрытие порта и окон. Не сохранять служебные настройки моста в рабочую сцену без необходимости.

#### Разметка артикуляции по готовой речи

Для речи из WAV/OGG доступен необязательный Rhubarb Lip Sync 1.14.0 (MIT, Windows, CPU). Установка и проверка закреплённого архива: `py -3.11 -B tools/skit/rhubarb.py --install`. Разметка: `py -3.11 -B tools/skit/rhubarb.py speech.wav --out out/WORK/audio/mouth.json`. Для неанглийской речи по умолчанию выбран менее точный независимый от языка `phonetic`; `pocketSphinx` предназначен для английского. Источник, версия, SHA-256 и параметры находятся в OPTIONAL_RESOURCES; среда хранится только в общей библиотеке.

Проверены запуск на русской записи, кириллица в путях, повторяемость, непрерывность отметок, паузы и окончание. JSON содержит provenance и не перезаписывает существующий результат. Это разметка форм рта, не готовая мимика: сопоставить формы с реально существующими morph/shape keys конкретного героя, добавить переходы и отдельно проверить речь, губы, челюсть, зубы, бороду и конец реплики в движении. Не выдавать технически корректные отметки за подтверждение точной русской артикуляции. Инструмент не определяет голос персонажа и не оценивает звук на слух; не добавлять его в сцены без речи.

#### Необязательные дополнения Blender

`py -3.11 tools/optional_addons.py retarget` устанавливает фиксированный Retarget 5.2.0 в общую локальную библиотеку; архив проверяется по SHA-256. GPL-3.0-or-later, Blender 5.0+. Источник и параметры — `docs/OPTIONAL_RESOURCES.json`. На Blender 5.3 проверены регистрация, диапазон анимации и штатный перенос 19 костей Invoker→Axe с последующим независимым bake. Bind работает через `INVOKE_DEFAULT` в реальном GUI-контексте `VIEW_3D`; headless-путь 5.2.0 завершается ошибкой `current_m=None` и не принят. Не добавлять скрытый патч этого поля и не повторять неудачную операцию поверх частично изменённой сцены. Перенос не исправляет пропорции и опору: в проверке стопы получателя скользили. Перед применением нужны согласование rest pose/масштаба, коррекция контактов и полный просмотр. Пальцы, лицо, одежда и дополнительные кости требуют отдельной карты/постановки. После принятой анимации запекать через штатный `nla.bake` с visual keying, отключать источник и проверять сохранение движения. Дополнение остаётся необязательным, автоматической заменой авторской анимации не является.

Чтобы включить его только в одном процессе Blender, перед скриптом сцены передать `-P tools/blender/enable_optional_addon.py`. Загрузчик проверяет архив и распакованные файлы, не сохраняет пользовательские настройки. `A8_RESOURCES` позволяет выбрать другую библиотеку. Не копировать код дополнения в собственные модули.

#### Ручные поправки материалов

В `render_scene.py` поле сцены `material_overrides` принимает точное имя материала и числовые входы `Alpha`, `Metallic`, `Roughness` (0–1), `Emission Strength` (от 0); например `{"material_overrides":{"имя материала кожи":{"Alpha":1,"Metallic":0}}}`. Это ручная поправка подтверждённого дефекта, не автоматическое распознавание игровых масок.

#### Устройство рендера

`render_study_frames.py` восстанавливает доступный GPU для Cycles даже при `--factory-startup`. `A8_CYCLES_DEVICE=AUTO` выбирает backend для GPU-сцены; CPU-сцена остаётся на CPU. Допустимы CPU, OPTIX, CUDA, HIP, ONEAPI, METAL; явно выбранный недоступный backend вызывает ошибку. Устройство записывается в manifest/report и не смешивается с прежним кэшем. Глобальные настройки Blender не меняются. В авторских скриптах применять ту же инициализацию устройства в каждом процессе: сохранённый в .blend флаг GPU не означает выбранный compute backend. Проверять фактический список устройств и время кадра.

#### Окружение

Для ручной 3D-постановки нужны Blender и FFmpeg/ffprobe. Python 3.11 используется внешними скриптами; скрипты с `bpy` выполняются Python самого Blender. Зависимости вспомогательного конвейера перечислены в `requirements.txt`. Они не устанавливают приложение или окно управления.

При необходимости создать изолированное окружение (Windows):

```powershell
py -3.11 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Команды руководства с `py -3.11` используют глобальный Python 3.11. Если зависимости установлены в `.venv`, в командах внешних Python-скриптов заменять `py -3.11` на `.venv/Scripts/python.exe`. Python внутри Blender запускается самим Blender.

Для 2D-конвейера дополнительно установить Chromium в этом окружении:

```powershell
.venv/Scripts/python.exe -m playwright install chromium
```

Пути задаются переменными окружения:

| Переменная | Назначение |
| --- | --- |
| `BLENDER` | Исполняемый файл Blender |
| `FFPROBE` | Исполняемый файл ffprobe; FFmpeg также доступен через PATH |
| `DOTA_ROOT` | Корень установленной Dota 2 |
| `S2V` | Source2Viewer-CLI |
| `A8_RESOURCES` | Общие локальные ресурсы; по умолчанию `cache/resources` |
| `A8_WHISPER_MODEL` | Локальная модель распознавания для проверки реплик |

`tools/paths.py` ищет Blender и Dota в установленных библиотеках Steam. Новые зависимости агент подбирает по задаче, проверяя происхождение, лицензию, совместимость и стоимость. Обязательной локальной LLM нет: сценарий и постановку может подготовить сам агент. Имеющиеся CLI-планировщики — ограниченные вспомогательные инструменты, а не обязательный способ создания ролика.

#### Игровые ресурсы и голоса

Игровые модели, текстуры и звуки извлекаются из установленной Dota; для русских голосов нужна русская озвучка. Source2Viewer можно указать через `S2V` или разместить в `cache/resources/source2viewer/`. Упакованная сцена Blender с разрешёнными ресурсами может рендериться без установленной игры.

Общие извлечённые декорации хранятся в `cache/resources/sets/`; голосовые модели — в `cache/resources/voice/`. Например, необязательный `tools/skit/character_voice.py` ожидает в `voice/character/` runtime `bin/llama-tts.exe`, GGUF модели и projector. Закреплённые источники некоторых ранее использованных компонентов сохранены в [OPTIONAL_RESOURCES.json](docs/OPTIONAL_RESOURCES.json); их наличие не означает обязательную загрузку. Другой подходящий локальный голосовой инструмент допускается после проверки.

Не загружать модели ради ролика без озвучки. Узнаваемость голоса и разборчивость проверять отдельно. Запуск платных сервисов и расходы требуют согласия.

#### Работа и проверка

Постановка и приёмка выполняются по [критериям качества](#quality-workflow), готовность — по [порядку проверки и сохранения состояния](#state). Результат передавать файлом доступным пользователю способом вместе с местом хранения исходников; локальная ссылка не гарантирует доступ с другого устройства.

Запуск подготовленного задания: `py -3.11 tools/blender/run_render_job.py путь/к/job.json`. Команды технических проверок и область их применения — в [карте инструментов](#tools). Формат 2D-сцен — в [справочнике](#scenes).

#### Передача проекта другому агенту или компьютеру

При очистке отличайте рабочие инструменты и ресурсы от результатов проверок: `qa/`, `_fv_work/` и `__pycache__/` создаются заново, а `cache/resources/` содержит программы и модели, `_game/` — необходимые игровые данные. Не удаляйте весь `cache/` как временный каталог. В `out/` могут находиться единственные исходники и принятые ролики; сначала проверяйте их зависимости. Старые ветки с уникальными коммитами сохраняйте в проверенном Git bundle перед удалением ссылок, а уникальные незакоммиченные файлы — отдельно. Архивирование не освобождает место и не должно называться физическим удалением.

При переносе рабочей папки отдельно проверять привязку проекта и текущего чата в приложении агента: копирование файлов и явный `workdir` отдельной команды не меняют эту привязку. До удаления старой папки открыть новый рабочий каталог в приложении, проверить запуск инструментов из него и только затем освобождать старые процессы. Если смена привязки недоступна через инструменты, сообщить пользователю конкретное необходимое действие до удаления, а не после потери просмотра или терминала.

В Git хранить актуальные инструкции, код, параметры и список ресурсов с происхождением. Для продолжения конкретного ролика передать его `.blend`, аудио, скрипт сборки/`job.json` и нужные локальные ресурсы. Проверить доступность этих файлов на новом компьютере; пути с предыдущего ПК не считать доступными автоматически. Агент фиксирует выполненное, границы проверки и следующий шаг в `project.json` работы; универсальные уроки обновляет в правилах этого руководства.

## Справочник формата 2D-сцен

### Сцены из JSON

Любой сегмент выпуска (`hook`, элемент `parts`, `outro`) может вместо готовой раскладки описать **сцену**: список элементов и таймлайн эффектов. Движок — `scene.js` + `scene.css`, анимация на GSAP (`vendor/gsap`, бесплатная лицензия GSAP). Рендер перематывает таймлайн сцены на время каждого кадра, поэтому кадры детерминированы.

```json
{ "voice": "…", "scene": { "bg": {…}, "cues": {…}, "items": […], "fx": […], "sounds": […], "camera": {…}, "cover": true } }
```

#### Настройки выпуска
| поле | значения |
|---|---|
| `transition` | `push` (сдвиг влево с размытием), `zoom` (наезд сквозь кадр), `flash` (вспышка). Без поля — переход темы. Стык режется прямо в движении, скорости совпадают |
| `subs` | `box` (белые плашки), `slam` (одно слово крупно), `line` (подчёркивание). Без поля — стиль темы |
| `theme` | ключ темы: `k`, `c`, `b` … |
| `show_header` | `false` скрывает верхнюю подпись канала и полоску прогресса. По умолчанию шапка видна |
| `sapi_voice` | Имя установленного русского голоса Windows, например `"Pavel"`. Для субтитров нужна заранее загруженная модель Whisper small |

Пример немой анимации из текстового запроса сохранён в
`episodes/study_eclipse.json`. Для черновика включите
`FV_SILENT=1` и `FV_DRAFT=1` и передайте сценарий и путь MP4 в
`video.py`. Запрос записан в `_prompt`, а расположение объектов и
время движения задаются в `scene` теми же полями, что у других выпусков.

`episodes/study_spacing.json` показывает озвученный черновик с графикой
и субтитрами. Запустите его через `video.py` с `FV_DRAFT=1`. В этом
режиме голос синтезируется Windows, а тайминги распознаются локальной
моделью. При `FV_SILENT=1` проверяется раскладка с условными таймингами.

#### Время
`at` — число секунд от начала сегмента, **метка** из `cues` (`"afk"`) или метка со сдвигом (`"afk+0.3"`). Метка — слово из озвучки: `"cues": {"afk": "AFK"}`.

Для предпросмотра своего сценария и точечной правки без озвучки
используйте одинаковые настройки черновика через `quickstart.py`.
В первой команде задайте исходник, во второй — его изменённую копию.
Пример заменяет кадры 18–23 с частотой 15 FPS.

```powershell
py -3.11 tools/quickstart.py 2d --scene исходник.json --out qa/my-scene/base
py -3.11 tools/quickstart.py 2d --scene правка.json --frames 18:24 --out qa/my-scene/edit
```

В манифесте ревизии укажите `base/preview.mp4`,
`edit/insert.mp4` и `replace_at: 18`. Кадры за пределами интервала
и дорожка исходного MP4 сохраняются. Для правки, меняющей длительность
или содержание речи, эти команды подходят только для проверки картинки.

Короткий акцент на элементе одной сцены можно задать текстом.
В запросе укажите ID элемента и время в секундах. Сначала соберите
исходный предпросмотр, затем передайте запрос с `--plan-only`, чтобы
увидеть диапазон кадров. Для применения повторите команду без этого флага.

```powershell
py -3.11 tools/quickstart.py 2d --scene episodes/study_eclipse.json --out qa/eclipse-accent/base
py -3.11 tools/quickstart.py 2d --scene qa/eclipse-accent/base/source.json --base qa/eclipse-accent/base/preview.mp4 --request 'Подчеркни sun на 1,4 с' --out qa/eclipse-accent/edit --plan-only
```

В новой папке будут изменённый `scene.json`, `plan.json` с запросом
и диапазоном, `revision.json` и итоговый `revision.mp4`. Исходники
сохраняются в `base`, для отката откройте исходный `preview.mp4`.
Перед применением сверяются контрольные суммы сценария и исходного
видео. Поддержан один короткий акцент на элементе верхнего уровня
без пересечения с другим изменением его масштаба. Для произвольной
правки картинки используйте команды с `--frames` выше.

Чтобы продлить паузу между эффектами в одиночной сцене без озвучки,
звуков, движения камеры и встроенных анимированных медиа, задайте
величину прибавки и момент паузы в секундах.

```powershell
py -3.11 tools/quickstart.py 2d --scene qa/eclipse-accent/base/source.json --base qa/eclipse-accent/base/preview.mp4 --request 'Продли паузу на 1 с после 3,2 с' --out qa/eclipse-accent/long-hold --plan-only
```

Для применения уберите `--plan-only`. План записывает прежнее и новое
время сдвинутых эффектов. Если выбранный момент попадает внутрь эффекта,
команда попросит выбрать другое время. При изменении длительности
собирается полный черновик `edit/preview.mp4` в папке правки.

##### Монтаж и точечные правки

Сначала соберите и проверьте каждый план через `tools/quickstart.py`.
Общий монтаж выполняется агентом через FFmpeg; для экспортированных Blender-планов
есть `tools/blender/assemble_shots.py` (формат аргументов — `--help`).
Прежний `project_preview.py` удалён вместе с приложением: его формат проекта
и автоматическое изменение отдельного плана больше не являются рабочим интерфейсом.
Голосовой предпросмотр 2D доступен через `quickstart.py 2d --local-voice`;
для него нужны русский SAPI, необязательный Python-пакет `faster-whisper==1.2.1` и заранее загруженная в локальный кэш модель `Systran/faster-whisper-small`. Установить пакет в тот же Python, который запускает предпросмотр: `.venv/Scripts/python.exe -m pip install faster-whisper==1.2.1` (или `py -3.11 -m pip install faster-whisper==1.2.1`, если используется глобальный Python). Для локального теста готовность модели проверить через `WhisperModel("small", device="cpu", compute_type="int8", local_files_only=True)`. Версия и хеши файлов модели перечислены в `docs/OPTIONAL_RESOURCES.json`. Проверяйте дорожку отдельно
и в итоговом монтаже.

Для точечной правки картинки сохраните копию выпуска и отрисуйте только
нужный диапазон. Номера кадров отсчитываются с нуля в частоте итогового
видео, правая граница не включается. Для черновика 15 FPS оставьте
`FV_DRAFT=1`, для 30 FPS снимите эту настройку. Поддерживается локальная
разметка речи через `sapi_voice` либо исходник без речи с `FV_SILENT=1`.
При SAPI сохраните прежний голос и текст, чтобы положение субтитров и меток
не сдвинулось.

```powershell
$env:FV_DRAFT='1'
py -3.11 video.py --picture-range 111:122 edited.json qa/spacing-edit/insert.mp4
Remove-Item Env:FV_DRAFT
```

В проверке выпуска `study_spacing.json` к маркерам `linear` и `eased`
добавлен одинаковый эффект `pulse` с `at: "start+5.24"` и `to: 1.3`.
Оба акцента приходятся на общий финиш, исходная озвучка остаётся в полном
ролике. Укажите `insert.mp4` в поле `insert` манифеста ревизии
и задайте `replace_at: 111`.

Числа должны быть конечными; неизвестная метка или неверный сдвиг — ошибка,
а не запуск в нулевую секунду. Это относится также к `start`, `in.at` и звукам.

#### Элементы (`items`)
Общие поля: `id`, `type`, `x`, `y`, `w`, `h` (px в кадре 1080×1920), `z`, `rot`, `color`, `bg`, `radius`, `pad`, `border` (цвет рамки карточки), `tex`, `tint`, `frame`, `cls`, `in`.

Цвета — токены `acc ink red mint gold rad dire paper navy dark` или любой CSS.

| type | поля | что это |
|---|---|---|
| `text` | `text` (`|` перенос, `*акцент*`, `_маркер_`), `size`, `font` (`display`/`body`/`cap`), `align`, `acc`, `fit` | заголовок, подпись |
| `chip` | `text`, `size`, `fill` | плашка-ярлык |
| `stamp` | `text`, `size`, `color` | потёртый штамп |
| `number` | `value` (`35:00`, `9 200`, `4,5`) | крупная цифра; с `fx: count` набегает |
| `img` | `src`, `fit` (`cover`/`contain`), `pos` | картинка в рамке |
| `hero` | `src` | герой целиком, низом на нижний край рамки |
| `card` | `src`, `label`, `stamp`, `icon` (для иконок) | карточка героя/предмета |
| `anim` | `anim` (ключ из `assets/anim`) | анимированный герой |
| `shape` | `kind` (`arrow`/`line`/`bracket`/`zig`), `stroke`, `color` | рисованный интерфейс |
| `row` / `col` | `items`, `gap`, `child` (общие поля детей) | ряд/колонка, делит место поровну |
| `panel` | `items` (координаты внутри панели) | контейнер с текстурой |
| `video` | `src` (`file:…mp4`), `from`, `dur`, `audio` (громкость звука клипа, 0 — без звука), `start`, `loop`, `hold` (`false` — виден только пока идёт) | клип из игры в рамке; кадры нарезаются под размер элемента |
| `model` | `hero` (ключ, напр. `juggernaut`), `anim` (имя анимации), `parts` (`all` или список), `yaw` (°), `zoom`, `tilt`, `fov`, `rim` (цвет контрового света), `key`/`ambient` (яркость), `speed`, `start`, `in_place` | 3D-герой из файлов игры с одеждой и оружием, анимация по времени сцены |
| `lottie` | `src` (`file:assets/lottie/….json`), `start`, `speed`, `loop`, `fit` (`cover`) | готовая анимация Lottie (например, с lottiefiles.com, бесплатные — формат Lottie JSON) |

**Мем** — `{"type": "meme", "name": "хэнк_понял", "x": 90, "y": 560, "w": 840, "h": 620, "in": {"fx": "pop", "at": "понял"}}`: кусок клипа вокруг лучшего момента (пик движения и громкости) со звуком, 1,6 с, виден только пока идёт (`dur`, `lead` — сколько до пика, `from` — свой старт, `hold: true` — оставить последний кадр). Каталог — `py -3.11 tools/memes.py` (`_game/memes/catalog.json` и лист `memes.jpg`); если автоматический момент мимо сути, точное время — в `_game/memes/peaks.json` (`{"хэнк_понял": 6.2}`), пересборку каталога оно переживает. Любой клип — тем же `video` с `src`. Чёрные поля клипа срезаются сами. Файлы мемов лежат локально в `_game/memes/` (не коммитятся), поэтому такой ролик рендерится локально.

`src`: `hero:juggernaut`, `item:blink`, `ability:kunkka_torrent`, `file:assets/…`, `game:panorama/images/minimap/dotamap.png` (картинки из файлов игры).

Для `video` начало выбирается по первому заданному значению:
`start` → `in.at` → `at` → `0`. Ноль — заданное время, `null` — пропуск.
`loop:true` повторяет изображение и звук до конца сегмента; `hold:false`
скрывает клип до старта и после окончания неповторяемого клипа. `hold:true`
оставляет крайние кадры, но не продлевает звук. При отрицательном старте
в начале сегмента используется соответствующая фаза клипа. Период равен
числу извлечённых кадров / fps: длинный WAV обрезается, короткий дополняется
тишиной. Звук клипа не переходит в соседний сегмент.

`child` в `row`, `col` и `panel` задаёт неглубокие defaults: поля отдельного
ребёнка заменяют одноимённые общие поля целиком. Они применяются до загрузки
медиа, поэтому наследуемые `src`, размеры, `audio`, `start`, `loop` и `hold`
учитываются при подготовке и при сведении одинаково.

#### Ресурсы из файлов игры (3D, миникарта, иконки)
Файлы игры хранятся локально в `_game/` и не публикуются в Git.
Экспортировать модели и текстуры следует установленным Source2Viewer CLI;
настройка путей описана в [подготовка](#setup). Старые обёртки
`vpk_tool.py`, `dota_export.py` и `map_crop.mjs` в текущий проект не входят.
Для 2D/Three.js героев нужны GLB в `_game/models/<герой>/`, для карты —
GLB и соответствующие текстуры. Для Blender есть `tools/blender/dota_map.py`.
Проверяйте экспорт, материалы, масштаб и совместимость анимаций до рендера.

#### 3D-площадка (`stage`)
`{ "type": "stage", "map": "river", "actors": [{ "hero", "anim", "x", "y", "z", "yaw", "phase", "speed", "scale", "splash" }], "cam": { "pos", "look", "to": { "pos", "look" } }, "fov", "sky", "sky_top", "fog_near", "fog_far", "water": { "color", "deep", "opacity" } }` — герои в настоящей карте: террейн смешивается из 4 слоёв как в игре (dota_map.js), вода своя под цвет дотовской, небо — градиент. Без `map` — простая река своей отрисовки. `ambience: "river"` в сцене — шум воды.

Дети контейнера получают id `родитель.0`, `родитель.1` … (если своего нет).
Все id, включая вложенные и унаследованные через `child`, должны быть уникальны
в пределах сцены. `stage.sun_dir` — ненулевой вектор из трёх конечных чисел:
он задаёт одно направление солнца для героев и многослойного материала карты.
По умолчанию `[6, 10, 6]` (координаты Three.js, Y вверх).

**Текстуры** `tex` — фото (Poly Haven, CC0): тёмные `wood oldwood doors metal plate stone blocks rock cliff leather forest`, светлые (тёмный текст) `planks rust cobble burlap concrete plaster`; бумага `paper parchment`; рисованные `noise grid scan halftone`. У всех фото-текстур фаска и затемнение; `tint` — свой оттенок поверх (например `["rgba(10,35,64,.5)", "rgba(10,35,64,.8)"]`). Новые текстуры — assets.yml, поле `textures`, список ключей: `?wood`, `?metal`, `?rock`.
**Рамки** `frame` (можно списком): `plate corners rivets tape ticket cap`. `tape` не сочетается с `corners`/`rivets`.
**Фон сцены** `bg`: `{"grad": [...]}`, `{"color": …}`, `{"tex": "grid"}`.

#### Появление (`in`)
Строка или `{ "fx", "at", "dur", "stagger", "dist" }`:
`fade rise drop pop slam left right wipe iris stamp draw` (для `shape`), для текста — `lines` (строки из-под маски), `chars` (по буквам), `type` (печать).

**Первый кадр ролика собран:** в первом сегменте всё, что появляется в первые 0,6 с, сразу стоит на месте (превью в ленте). Выключить — `"cover": false`.

#### Эффекты (`fx`)
`{ "target", "fx", "at", … }`. Цель: `"id"`, `"id.*"` (все дети), `"id em"` (CSS внутри), `"@all"` (вся сцена).

| fx | параметры | что делает |
|---|---|---|
| любое из `in` | | появление по метке |
| `pulse` | `to` | короткий удар масштабом |
| `shake` | `dur` | тряска |
| `jump` | `dist` | буквы акцента подпрыгивают волной |
| `gray` / `color` | | обесцветить / вернуть цвет |
| `dim` / `show` / `hide` / `out` | `to` | приглушить, показать, скрыть, увести вверх |
| `move` | `x y scale rot ease` | сдвиг |
| `mark` | | маркер под `_словом_` |
| `stamps` | | штампы на карточках (`stamp` у `card`) |
| `count` | `dur ease` | число набегает от 0 |
| `swap` | `text` | смена текста переворотом |

#### Камера
По умолчанию медленный наезд 1 → 1,03 за сегмент. `"camera": {"from": 1, "to": 1.06, "x": 0, "y": -40}` или `false`.

#### Звуки (`sounds`)
Синтезированные, тише голоса: `{ "kind": "stamp|bubble|tick|pop|whoosh", "at": "метка+0.2", "gain": 1 }`.

#### Проверка описания
Перед озвучкой проверяются типы, текстуры, рамки, эффекты, звуки, цели,
уникальность id и объявление меток. Ошибки печатаются строками `⚠` и останавливают
сборку. После озвучки повторно проверяется разрешённое время: ненайденное слово
также останавливает сборку. Это проверка описания, не художественная приёмка.

Сценарии считаются доверенным локальным кодом: текст допускает HTML,
`file:` обращается к локальным ресурсам, браузер имеет расширенный доступ
для рендера. Не запускать непроверенный чужой JSON как изолированный документ.
Проверки выше не являются защитной средой для недоверенного импорта.

#### Что ещё делает рендер
- Обложка: первый кадр сохраняется рядом с роликом как `cover_<имя ролика>.png` (для `facts_NNN.mp4` — `cover_NNN.png`). Автоматической публикации нет.
- В этом 2D-конвейере громкость по умолчанию выравнивается к −14 LUFS. Это локальная настройка, не универсальное требование платформ.
