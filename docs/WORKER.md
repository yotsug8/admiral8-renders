# Дополнительный компьютер

Первое применение — независимые CPU-проверки, анализ готовых кадров и сборка
видео, пока основной компьютер рендерит. Пригодность второго GPU проверять
одинаковой короткой сценой: полное время с передачей файлов, качество и ошибки.
Наличие второго компьютера само по себе не обещает ускорение.

## Если на обоих компьютерах уже есть Codex

Сначала проверить встроенное подключение: на дополнительном компьютере
«Настройки → Подключения → Управление этим компьютером», на управляющем —
«Управление другими устройствами». Доступность зависит от версии приложения.
Сопряжение выполнить в интерфейсе владельцем; подтверждения и коды не публиковать.
Для этого способа отдельный сервер OpenSSH не требуется. Сначала убедиться,
что дополнительный компьютер действительно появился среди доступных сред.
Это не переносит локальные игровые ресурсы и не создаёт копию проекта.

Источник: [подключение устройств Codex](https://learn.chatgpt.com/docs/remote-connections).

## Альтернативное соединение по SSH в домашней сети

На дополнительном Windows-компьютере, в PowerShell администратора:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-NetFirewallRule -Name OpenSSH-Server-In-TCP -RemoteAddress LocalSubnet
Start-Service sshd
whoami
ipconfig
```

Это установка штатного компонента, а не готовое подключение. Если установка
требует перезагрузки или выдаёт ошибку, сначала завершить её. Получить имя
учётной записи и IPv4 активного адаптера. Пароли не передавать в чат.
Вход настроить отдельным SSH-ключом; приватный ключ остаётся на управляющем
компьютере вне git. Отпечаток ключа сервера сверить на самом дополнительном
компьютере перед первым соединением. Не отключать проверку ключа сервера.
После проверки адресов ограничить правило брандмауэра адресом управляющего
компьютера. Проброс порта на роутере для этого сценария не нужен.

Устанавливается только сервер SSH, настройки сна и автозапуск не меняются.
Для отключения доступа: `Stop-Service sshd`. Правила доступа и ключи удалять
только относящиеся к этой настройке, сохраняя существующие подключения.

Официальный источник: [OpenSSH в Windows](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse).

## Организация работы

- Отдельная копия репозитория на фиксированном коммите; результаты складывать
  в отдельную папку задания. Одновременные записи в общие `_fv_work` и `qa`
  запрещены. Основную рабочую копию по сети не использовать.
- Сначала проверить доступ и версии, затем передать только нужные ресурсы
  по списку с SHA256. Полный перечень внешних зависимостей — LOCAL_FILES.md.
- Первая задача: сборка готовых PNG и WAV существующим assemble_study.py.
  Проверить параметры MP4 и декодированные кадры; одинаковый SHA256 MP4 между
  разными версиями кодировщика не обязателен. Зафиксировать версии.
- Для рендера отдельно проверить Blender, движок, текстуры и совпадение
  изображения. Не отправлять неизвестную сложную сцену сразу целиком.
- Не копировать токены, личные файлы и настройки игры. Озвучку повторно не
  заказывать: готовый WAV передаётся как ресурс задания.

Подключение считается выполненным только после успешной удалённой команды,
передачи тестового файла и возврата проверенного результата.

Первое облегчённое задание без игровых ресурсов: скачать опубликованный MP4
из renders, сверить SHA256, запустить `assemble_study.decoded_qa` с его рецептом
и осмотреть извлечённые кадры/склейки. Для этого достаточно отдельной venv с
Pillow, NumPy и imageio-ffmpeg; Python 3.10 допустим для этой ограниченной пробы,
но не объявляется заменой требуемого проектом Python 3.11. Не переустанавливать
системный Python ради первого замера. Проверка ролика не равна проверке скорости
Blender или полного окружения сценок.

Подтверждённая первая проба — [worker_v7_result.json](studies/worker_v7_result.json): независимый компьютер получил опубликованный MP4, сверил хеш и выполнил анализ/извлечение кадров за 3,370 с. Установка и осмотр в этот замер не входят. Преимущество относительно основного ПК и скорость Blender не измерены.

## Рабочая очередь после подготовки

Текущие задания и следующий шаг находятся только в активной очереди
PROJECT_STATE.md. Настройка окружения — завершённый этап, а не задача,
которую следует повторять при каждом сообщении. Ограничения конкретного
этапа подготовки не подменяют более позднее разрешение на код и рендер;
действующие запреты пользователя сохраняют силу.

- Перед выдачей задачи проверить текущий статус и рабочую папку/ветку.
  Не клонировать новые дубликаты из-за отсутствия готового отчёта.
- На исполнителе сохранять локальный `_game/worker_task.json`: текущая
  задача, исходный commit, разрешённые файлы, выходная папка, этап, команда
  и PID текущего процесса, следующий шаг и результаты проверок. После
  передачи контекста читать его вместе с последним назначением, прежде
  чем выполнять старый установочный prompt. Это журнал исполнения,
  не источник новых разрешений. Общая очередь остаётся в PROJECT_STATE.md;
  ветка задания может содержать устаревшую копию этого документа.
- При закрытии процесса записать exit code и реальные артефакты. Перед
  заявлением о работе машины проверить PID, рост числа кадров или свежий
  лог; подготовка кода и работа рендера — разные состояния. Не оставлять
  «жду рендер» финальным результатом, если можно дождаться своего процесса.
- Выдавать независимый результат: конкретное упражнение, список разрешённых
  файлов, критерии проверки, папку вывода и следующий этап. Игровые ресурсы
  не нужны для упражнений на манекене; второй компьютер может рендерить их
  на CPU одновременно с основным GPU.
- Различать «сообщение отправлено», «начата работа», «рендер завершён»,
  «результат проверен» и «интегрирован». Молчание, idle или окончание одного
  процесса не означают, что вся задача выполнена.
- После проверки результата сохранить код/метод в main и медиа в renders,
  сверить передачу по SHA256 и выдать следующий разрешённый блок свободному
  исполнителю. Не требовать нового «продолжай» для уже порученной очереди.
- Ведущий проверяет полученный diff и воспроизведение; исполнитель публикует
  только свои файлы в собственной ветке. Не отправлять неподтверждённые
  изменения в общие main/renders и не коммитить соседние незавершённые пробы.
- Две неудачные осмысленные пробы одного подхода требуют записать причину и
  пересмотреть подход. Пороги проверки не ослаблять ради формального pass.

Подтверждённый CPU-результат: `studies/FOLLOWTHROUGH.md`, 135 кадров/30fps,
Cycles CPU, построение и рендер около 148 с на дополнительной машине.
Исходник повторно построен и проверен на основной; MP4 совпал по хешу.
Этот замер не переносится на игровые сцены и другие настройки.
