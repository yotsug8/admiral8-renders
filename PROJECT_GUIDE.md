# Admiral8 Renders — единое руководство

Это единственный основной документ с инструкциями проекта: правила, ТЗ, запуск, проверки, состояние и накопленный опыт. AGENTS.md и README.md служат только входами сюда. Лицензии сторонних компонентов и машинные данные ресурсов остаются возле соответствующих файлов; они не являются отдельными правилами работы.

## Как пользоваться и обновлять

- Перед работой прочитать правила и текущее состояние, затем по карте ниже открыть относящиеся к задаче разделы ТЗ, подготовки, уроков и справки. Не перечитывать неизменённый полный документ в каждом шаге: использовать якоря, заголовки и узкий поиск; карта не заменяет исходник перед правкой.
- Свежий запрос пользователя определяет задачу. Внутри проекта актуальные правила и состояние имеют приоритет над историческими записями; старые статусы и планы не являются поручением продолжать закрытый ролик. Это не меняет приоритета системных и разработческих инструкций среды.
- Новое постоянное требование редактировать в разделе правил, состояние — в разделе состояния, причины и проверки конкретной ошибки — в опыте сцены. Не заводить ещё один файл инструкций и не копировать одно правило в несколько действующих документов.
- Одинаковое требование в исходном полном ТЗ и практических критериях имеет один смысл, не требует двойной проверки. Полный текст ТЗ сохранён; история содержит доказательства решений, а не второй набор действующих правил.
- Длинные истории исправлений раскрываются по необходимости. Они не заменяют обязательные сводные уроки перед похожей работой.

## Быстрая карта проекта

Инструкции и состояние — только здесь. Навигация по коду: `py -3.11 tools/project_map.py`; подробности нужной области: `--area render --symbols`, поиск пути: `--find contact --symbols`, контроль актуальности: `--check`. Индекс проверен по 29 действующим точкам входа и читает текущие исходники, не хранит вторую копию кода и не требует ИИ, сервера или новых пакетов. Он сокращает лишние чтения, но экономия токенов не измерена; обещание «в 70 раз» не подтверждено.

В Git — технический конвейер, входы проверок, лицензии и это руководство. `out/` — локальная работа и исходники роликов, `qa/` — проверочные данные, `cache/resources/` — программы/модели/референсы. Они не являются мусором целиком. Одноразовые скрипты закрытых роликов находятся рядом с их сценами в `out/*/source/`, прежний код также доступен в истории Git. `docs/OPTIONAL_RESOURCES.json` — только каталог необязательных ресурсов, не инструкции.

## Правила работы

### Правила проекта

Отвечать по-русски. Применять свежие уточнения пользователя и сохранять чужие изменения.

Ответственность распространяется на весь репозиторий: перед работой восстанавливать актуальный контекст по ТЗ, состоянию, документации и исходникам затрагиваемых компонентов; учитывать зависимости и последствия дальнейших изменений. Не требовать от пользователя повторять уже записанные требования. Статус документа не заменяет проверку фактических файлов, а работа над одной сценой не отменяет соблюдения общих требований проекта.

- Основной сценарий — пользователь передаёт ИИ-агенту ссылку на репозиторий и запрос на видео. Агент самостоятельно готовит окружение, ставит сцену в Blender, проверяет движение и звук, собирает MP4 и сохраняет исходники. Отдельное приложение, GUI, установщик и ZIP-запуск исключены из проекта; не восстанавливать их без нового явного запроса.
- Сначала проверить исходник и зависимости. Для сцены проверить общий силуэт, геометрию, контакты, свет и звук дешёвыми пробами. После изменения окружения проверить каждый используемый ракурс на перекрытие камеры геометрией; выборка крупных планов не покрывает общие планы. Один GPU-рендер за раз. Для рук и реквизита проверять реальный контакт и деформацию с двух сторон.
- После изменения сверять запрос с фактическим кадром, движением и звуком. Техническая проверка не подтверждает художественную оценку. Оценивать результат строго: самостоятельно выявлять видимые недостатки, не считать затраченное время или успешный рендер основанием для поблажек. Известный заметный дефект исправлять до показа либо прямо обозначать как нерешённый. Фиксировать границы проверки в текущем состоянии проекта.
- После правок кода запускать `py -3.11 tools/check.py` и целевые проверки. [SETUP.md](#setup) описывает работу агента в новом окружении. Перед коммитом просматривать diff, добавлять только относящиеся к задаче файлы. Автор коммита — `Codex <codex@openai.com>`.
- Использовать бесплатные локальные средства. Проверять версии, происхождение и лицензии новых зависимостей. Публикация, расходы и необратимое удаление уникальных данных требуют разрешения.
- Перед загрузкой крупных моделей и серийным рендером проверять запас места для самих файлов, временной распаковки и кадров. После переполнения диска проверять целостность созданных медиа; существование файла не подтверждает успешную запись. Уникальные сцены не удалять ради освобождения места.
- После проверки закрывать открытые для неё проигрыватели и завершать сеанс захвата экрана. Если жёлтая рамка Windows остаётся, проверить завершение процесса захвата; закрытие проигрывателя само по себе не подтверждает остановку захвата. Чужие окна и фоновые рендеры не закрывать.
- В Git хранить код, необходимые ресурсы, короткую инструкцию и актуальное ТЗ. Файлы Dota, веса моделей, отчёты, ключи, временные файлы и готовые ролики держать локально. Медиа в чате показывать абсолютным путём. Локальный путь доступен на исходном ПК.

#### Постоянные критерии качества

- Перед показом каждой новой версии видео проводить обязательный художественный разбор полного монтажа в рабочем темпе: смысл и постановка, композиция, темп и движение, анатомия/деформация, контакты реквизита, материалы, свет/мерцание и звук. В документации сцены фиксировать конкретные находки, выполненные исправления, границы фактической проверки и оставшиеся недостатки. Успешный рендер или отсутствие технических ошибок не являются допуском к показу. Заметные дефекты исправлять до выдачи, затем повторно проверять изменённый участок и стыки. Непроверенный аспект не объявлять пройденным. Не превращать проверку в бесконечное расширение задачи: устранять выявленные недостатки согласованной сцены, а не добавлять новые идеи при каждом просмотре.

- Для главного перехода размечать начало подготовки, атаку звукового эффекта, визуальную кульминацию и появление результата в секундах и кадрах. Сверять с референсом и дорожкой; одиночная вспышка на склейке не заменяет содержательное изменение окружения. Отдельно фиксировать просмотр референса, анализ тайминга и фактическое прослушивание — не выдавать одно за другое.
- На склейке сохранять смысловой ориентир, если действие связано с препятствием или раскрытием героя из-за него. Проверять пару кадров до/после и переход в рабочем темпе: крупный читаемый герой не компенсирует исчезновение колонны, двери или другого сюжетно важного объекта.
- Перед пародией на известную сцену установить участников, смысл происходящего и причинную последовательность по референсу и при необходимости первоисточнику. Переносить в Dota роли, намерения, реакции и ключевой монтаж. Не подменять узнаваемую сцену произвольной шуткой по внешнему сходству кадра. До показа сверить смысл и последовательность с исходным фрагментом.
- Образное сходство с персонажем референса не означает буквальную замену цвета кожи или игрового облика. Согласованные изменения силуэта и характера переносить на узнаваемую модель героя. Сохранять смысловую географию действия (лестницу, высоту наблюдателя, препятствия), проверять опоры архитектуры. Для слышимой речи ставить артикуляцию по реплике и её времени, отдельно проверяя рот в крупных планах и опору стоп на каждой ступени.
- После изменения пропорций персонажа повторно проверять стык головы и туловища, включая открытый рот и повороты. Закрывать щели геометрией с правильными весами и текстурой; маска, тень и ракурс не считаются исправлением. Сначала установить фактическую открытую кромку сетки и поверхность соединения, не подменять их приблизительной вставкой. Для поднятой маски проверить физический контакт с волосами/лбом с двух сторон; положение выше лица само по себе не подтверждает посадку. Посадку носимого предмета сверять с анатомическими ориентирами, а кадрирование — с полным силуэтом предмета и его движением.

- Пользовательские примеры в именах файлов и описаниях обозначать нейтральными идентификаторами без названий каналов. При переименовании обновлять ссылки и проверять сохранность содержимого; не выдавать анонимизацию названий за удаление водяных знаков или метаданных внутри медиа.

- При разборе пользовательских референсов отделять наблюдаемый приём от предположения о технологии и от случайного дефекта. Для короткой постановки заранее определять понятный вход, изменение ситуации и завершающую реакцию; крупности и движения камеры выбирать под смысл, а не ради разнообразия. Разбор текущей подборки — [PROJECT_GUIDE.md#references](#references).
- Живость персонажа проверять по вниманию, выражению лица, согласованию головы/корпуса/рук и реакции на партнёра. Не заменять эмоциональную постановку непрерывной ходьбой, тряской или одинаковой активностью всей группы. Намеренный гротеск и масштабный контраст должны читаться как замысел и не оправдывают случайные дефекты контакта и анатомии.

- До дорогого общего рендера собрать короткие проверки всех рискованных узлов в один проход: хват и одежда, выпуск предмета, реакция на попадание, падение и покой, свет и эффекты. Повторные локальные исправления без проверки целой последовательности затягивают работу и возвращают уже устранённые дефекты. После просьбы закончить не расширять объём новыми улучшениями; довести согласованный проход до полного файла. Оценивать срок по измеренной скорости и оставшимся кадрам, отдельно учитывать сборку и просмотр.
- Для возобновления рендера сохранять хеш сцены, настройки и происхождение кадров. Повторно использовать кадры только после проверки, что изменения не влияют на их геометрию, материалы, свет, камеры и эффекты; существование PNG не подтверждает целостность. После паузы продолжать с проверенных недостающих кадров, затем проверять полный MP4 и стыки. Принятую пользователем версию и закрытие задачи фиксировать явно; согласие оставить результат не означает поручения запускать ещё один рендер.

- До изменения ролика прочитать применимые разделы ТЗ, правила и документацию сцены; составить конкретную проверку результата по ним. Не считать прежнюю запись «готово» приёмкой после нового замечания. Проверять мелкие дефекты в исходном масштабе и в размере экрана телефона, полный монтаж — в рабочем темпе; выборка кадров не подтверждает отсутствие ошибок между ними.
- Скорость модели проверять вместе с пройденным расстоянием, масштабом сцены, FPS и характером усилия. Падение должно ускоряться и завершаться понятным контактом; растягивание траектории на длительность ролика не оправдывает зависание или слоумо. Фоновое событие может закончиться раньше ролика. Проверять весь видимый отрезок при целевых FPS и переход к покою.
- Перед серийным финалом проверять рискованные широкие планы при итоговом разрешении: дешёвый черновик не выявляет переполнение буфера теней EEVEE. Контролировать предупреждения Shadow buffer full, увеличивать ёмкость в пределах VRAM и пересчитывать весь затронутый план. Увеличение разрешения само по себе не подтверждает сохранность теней.
- При экспорте sRGB PNG явно задавать согласованные матрицу RGB→YUV, диапазон и метаданные: tools/media_color.py используется Blender-экспортом и браузерным PNG-кодировщиком. Одни теги без преобразования матрицы могут исказить цвет. Проверять реальный encode/decode на светлых, тёмных и цветных образцах; это не заменяет художественную цветокоррекцию или проверку конкретного телефона. Этот путь не предназначен для произвольного HDR-видео.
- При ряби проверять не только сэмплы и денойзер, но и композитинг, маски глубины, прозрачность и объёмы. Сравнивать один кадр до/после композитинга, затем последовательность. Не использовать несглаженную глубину как финальную маску на дыме, листве и motion blur без визуальной проверки.
- Рябь на стыке объектов проверять на дублирующиеся и совпадающие поверхности (z-fighting). Устранять перекрывающиеся грани или объединять геометрию; увеличение сэмплов не исправляет конфликт глубины. После изменения хвата проверять весь объём реквизита относительно корпуса и окружения на всей видимой последовательности, а не только контакт рукояти с ладонью. Допустимый контакт пальцев не считать проникновением в торс.
- Видимую полосу или «дыру» сначала диагностировать: отдельно проверить геометрию, нормали, материал и свет. Граница освещения может выглядеть как шов; отсутствие геометрического отверстия не означает приемлемый кадр. Соседние поверхности пола сверять по реальной высоте и фаскам, архитектурные элементы — по видимой опоре и назначению. Согласовывать износ собственных моделей с игровыми ресурсами, не пытаться исправить несогласованную форму одной текстурой.
- Проверку контактов с окружением проводить с видимым окружением: скрытая колонна или стена делает такую пробу непригодной для приёмки. До общего рендера изменённого действия просмотреть короткую последовательность с рабочей камеры и проблемный контакт с двух сторон. Отсутствие пересечений сеток не подтверждает читаемый зазор в кадре.
- После усиления мимики или наклона головы проверять бороду, волосы, воротник и наплечники относительно груди на всей реакции, включая открытый рот и возврат в позу. Проверять фактическое направление движения рига в мировых координатах; название оси и знак поворота не доказывают отклонение назад. Для длинной бороды согласовать её отдельную кость с движением головы и инерцией.

- При замене анимации после ретайминга проверять старые дробные ключи и движение на долях кадра: ровные целочисленные позы не исключают рывков и смаза между ними. Удалять ключи обратным индексным проходом, затем проверять фактическое отсутствие конфликтующих ключей и повторять пробу с motion blur.

- Для непрерывного действия не обнулять скорость у каждой промежуточной позы. Убирать непреднамеренные удержания и торможения, сохраняя раздельные смысловые контакты. Проверять переходы между жестами в рабочем темпе: плавность не должна превращаться ни в простои, ни в наложение кульминаций.

- Если повторные исправления хвата ухудшают позу, сохранить отклонённую версию и пересобрать движение от проверенной исходной позы рига. Не наследовать накопленные компенсирующие повороты. Сначала проверить всю цепь плечо–локоть–кисть и деформацию сетки, затем посадку предмета; подтвердить результат короткой последовательностью с двух сторон и в рабочей камере.

- Технический способ выполнения и проверки выбирать самостоятельно по результату, не ждать от пользователя предложения открыть приложение или сменить инструмент. Если скрипты и отдельные пробы повторно пропускают визуальную ошибку, менять способ диагностики: осматривать сцену интерактивно, изолировать проблемную геометрию, проверять несколько ракурсов и непрерывное движение. Открытое приложение и выполненный расчёт сами по себе не подтверждают качество результата.
- Самостоятельно устранять заметные ошибки до показа: пользователь не должен повторно находить перекрученную кисть, неверный хват или пропавший реквизит. Проверять поверхность ладони, объём запястья и положение предмета в крупном плане с нескольких сторон и на всей дуге действия. Совпадение с оружейной костью, успешный расчёт IK и один удачный кадр не подтверждают правильный хват; после исправления повторять визуальную проверку, включая выпуск и последующее действие.
- Использовать игровые анимации только там, где они подходят действию. Для нестандартного жеста, стрельбы из другого оружия, броска, реакции на взрыв и продолжения действия ставить собственную анимацию; не склеивать неподходящие игровые клипы. Проверять подготовку, действие, последствия и выход из него в рабочем темпе. Не возвращать героя в нейтральный idle сразу после напряжённого события.
- Избегать механической очереди изолированных жестов. Взгляд и перенос веса могут начинать следующее действие до завершения предыдущего, рука и корпус продолжают движение после усилия. Уверенность выражать устойчивой опорой, ясным намерением и свободной работой плеч, а не случайной тряской. Если действиям тесно, увеличивать длительность постановки и менять монтаж, сохраняя естественные скорости замаха, броска и реакции.
- Фоновое событие не превращать в самостоятельный эпизод без сюжетной необходимости: не отдавать ему отдельный крупный план, громкий звуковой акцент или реакцию героев, отвлекающие от основного действия.
- Не подменять отдачу сильной тряской персонажа. Проверять вместе скелет, одежду, манжеты и отдельные навесные детали по всей последовательности; отлетающий рукав или рывок аксессуара считается браком даже при совпадении ладоней с оружием. Скорость монтажа должна оставлять время прочитать контакт и последствие.
- Замечание о спешке исправлять локальным таймингом подготовки и контактов, не замедлением всей сцены. Для проверки боевой анимации сохранять рабочие 30 FPS; разреженный рендер не подтверждает плавность. После ретайминга проверять фазу шага, скорость продвижения и непрерывность вращений на каждом стыке.
- Звук автоматического оружия должен иметь читаемые атаки, плотную очередь и прекращение огня; короткий периодически повторённый срез и постоянные синусоидальные тоны могут превращать его в гул. Проверять оружие отдельно и в сведении. Отклонённые голосовые пробы не переносить в следующий ролик; узнаваемость не выводить из имени модели или игрового референса.
- Для падений и взрывов анимировать направленную реакцию на конкретное событие, контакт с рельефом и окончательную остановку. Не заменять их одинаковыми клипами смерти, перемещением целого тела по дуге или вспышкой без столкновения. Проверять пересечения транспорта, роторов и тел с картой до общего рендера.

- После изменения стойки, корпуса, плеч, локтей или положения оружия заново проводить визуальную проверку хвата. Прежняя проверка больше не действует, даже если численное положение пальцев относительно рукоятки сохранилось. До общего рендера проверять полный силуэт и деформацию всей руки с трёх сторон, затем непрерывное движение.
- При постановке жеста решать плечо, локоть, предплечье и кисть как одну цепь. Не сохранять прежнюю мировую ориентацию кисти после перемещения локтя: это может скрутить предплечье даже при правильной точке контакта. Проверять естественный изгиб и объём запястья, касание поверхности, отход и возврат руки с двух сторон и в движении.

- Не принимать рекламные обозначения «realistic», размер файла или число полигонов за качество ресурса. До включения в сцену визуально сравнивать модель с героями: силуэт, конструктивные детали, текстуры, стекло, металл, ткань и следы износа при общем свете. Если реквизит выглядит игрушечным или примитивным рядом с игровыми героями, заменить ресурс; затемнение и постобработка не исправляют недостаток геометрии и материалов.

- При совмещении отдельно импортированных героев и карты сверять единицы и коэффициенты масштаба до постановки. Уменьшение героев без согласованного изменения окружения недопустимо. Проверять рост относительно дороги, растительности и архитектуры в общем плане; после изменения масштаба повторно проверять опору ног, препятствия и все камеры.

- Переводить существенные замечания пользователя и повторяющиеся ошибки в постоянные правила репозитория. Записывать причину, требуемое поведение и проверку перед показом. Общие правила обновлять здесь, выводы по конкретной сцене хранить в её документации. Применять правила в следующих работах.
- Учитывать устройство просмотра: локальная ссылка на ПК не доставляет материал пользователю на телефоне. Для удалённого просмотра передавать сам файл доступным способом; загрузку, доступ и воспроизведение проверять раздельно. Не просить оценивать недоступный материал.
- У физического взрыва отдельно проверять видимую форму частиц: не оставлять одинаковые кубы или другие заметные примитивы вместо обломков. Согласовывать сколы с материалом поверхности, варьировать форму и размер. Проверять весь разлёт и столкновения: отскок и вращение затухают, частицы не продолжают крутиться на зажатой высоте. Такой дефект исправлять до показа, а не оправдывать условностью эффекта.
- Для узнаваемого элемента Dota сначала искать исходную модель, текстуры, анимацию, эффект и звук в установленной игре. Для способностей проверять ссылки на ресурсы в игровом описании эффекта. Сохранять узнаваемый силуэт, цвет и движение. Избегать произвольных сфер, декоративных точек и экранных колец вместо существующих игровых эффектов.
- Ключевой эффект или реквизит должен читаться на экране телефона. Проверять крупность в рабочем кадре и усиливать масштаб в смысловой кульминации, сохраняя видимость героя и точки контакта.
- При создании или удержании предмета двумя руками проверять его положение относительно обеих ладоней на каждом кадре удержания. Для перехвата отдельно проверять рабочий ракурс: направление движения, оружие, точка касания и реакция должны читаться раздельно. Совпадение точек в 3D не подтверждает понятную постановку.
- До чистового рендера смотреть черновой монтаж целиком в рабочем темпе. В цепочке действий сначала показать исходное положение предмета и намерение героя, затем контакт и видимое последствие. Проверить, что без звука понятно, кто действует, на что и что изменилось. Если это теряется на склейке или за эффектом, переставить действие или камеру и повторить проверку.
- Для движущегося эффекта проверять все переходы между контактом и свободным движением. Пока эффект удерживают, его движение должно следовать за руками или реквизитом. После отпускания направление и скорость должны продолжать видимое действие. Проверять стыки покадрово и в рабочем темпе, включая склейки.
- Не заканчивать привязку эффекта к ладоням раньше видимого перехвата: отдельная красивая траектория создаёт впечатление самостоятельного полёта. До контакта вычислять положение из ладоней, при переносе — из точки удержания реквизита. Показывать подход, касание и начало переноса в непрерывном плане; проверять весь интервал удержания и проход реквизита мимо обоих героев.
- Окружение и реквизит согласовывать с героями по масштабу, материалам и детализации. Для ключевого предмета сначала проверить игровые исходники. Если подходящего нет, подобрать или изготовить модель с читаемым силуэтом и правдоподобной поверхностью. Проверять предмет в крупном плане при свете итоговой сцены, его опору, а общий план — на края декораций, пустоты и случайную расстановку.
- Для всех моделей выбирать наиболее качественные доступные и совместимые исходники. Это относится ко всей сцене: персонажам, противникам, карте и рельефу, деревьям, камням, растительности, разрушениям, укреплениям, оружию, реквизиту и технике. До рендера сверять LOD, геометрию, реальные размеры текстур, нормали, UV и материалы в общем освещении. При наличии оригинальных карт высокого разрешения сверять их с используемой сеткой. Различать кожу, ткань, дерево и металл в шейдерах. Проверять изменения материалов и постобработки на одинаковых кадрах с теми же позой и камерой.

После цветовой правки сравнивать те же планы и при необходимости восстанавливать детали локальным заполняющим светом. Сохранять контактные тени и читаемость лиц, реквизита и значимого окружения. Рябь и мерцание оценивать на последовательности кадров в реальном темпе.
- Проверять кисть, пальцы, ладонь и реквизит с двух сторон. Предмет должен опираться на поверхность хвата, пальцы обхватывают его без выворачивания запястья. Проверять проход оружия относительно предплечья, корпуса и окружения по всей дуге, включая смену хвата.
- Проверять героя с оружием целиком, а не только крупные фрагменты и координаты контакта: полный силуэт, плечи, локти, запястья, пальцы, весь предмет и его положение относительно корпуса — спереди, сбоку и сзади, затем весь черновик в движении. Сначала проверить конструкцию предмета и крепление рукояток, потом ставить руки. Не подгонять позу под ошибочную геометрию и не выдавать совпадение центров хвата за правильный хват. До показа самостоятельно выявлять смещённые рукоятки, вывернутые кисти, пересечения манжет и оружия.
- Для неорганизованной толпы избегать одинаковых дистанций, ровных рядов и синхронных циклов. Различать направления, скорости, фазы шага и реакции на препятствия; проверять общий план и движение целиком. Напряжение боевой сцены выражать осмысленными действиями героев — перемещением, переносом веса, укрытием, взглядом и реакцией на угрозу, а не только эффектами и тряской камеры.

- Проверять передачу работы новому агенту: README, правила и настройка должны приводить от запроса к сцене и проверенному MP4 без приложения и скрытого контекста предыдущего чата. Не подменять запрос готовым примером. Указывать необходимые локальные ресурсы и фактические ограничения инструментов.

- При переносе сцены в другое пространство согласовывать фон, освещение, отражения и исчезновение окружения. Качественный фон сам по себе не подтверждает качество перехода: проверять масштаб деталей, границы масок и мерцание при движении камеры. Одинаковые точки и широкая неоновая обводка не заменяют художественную постановку космоса.

- При улучшении качества сохранять явно предпочитаемые пользователем ритм и акценты. Разделять мягкость постановки, глубину резкости, смаз и потери от разрешения/перекодирования. Собирая очередную версию, брать исходные кадры, а не цепочку уже пережатых монтажей. Краткий эффект проверять вместе с читаемым кадром до и после него; смешивание изображения с его негативом может дать серый провал вместо вспышки.

- Выходные пути Blender и других внешних инструментов задавать абсолютными. Проверять файл именно по ожидаемому пути, журнал выполнения и manifest: завершение процесса само по себе не подтверждает успешное создание результата.

3. Найти установленные Blender, Python, FFmpeg и ffprobe. Для Dota найти игру и Source2Viewer. Проверить версии, доступную память, GPU и место для кадров. Использовать имеющиеся рабочие инструменты прежде загрузки новых.
4. Создать отдельную локальную папку ролика, сохранить сценарий, сцены, скрипты, звук и журнал решений. В Git хранить переиспользуемый код и документацию; крупные игровые файлы и готовые видео — локально.
5. Проверить постановку дешёвыми пробами. Затем собрать полный черновик, просмотреть его в рабочем темпе и показать пользователю. Чистовой рендер выполнять по согласованному запросу.

#### Окружение

Для ручной 3D-постановки нужны Blender и FFmpeg/ffprobe. Python 3.11 используется внешними скриптами; скрипты с `bpy` выполняются Python самого Blender. Зависимости вспомогательного конвейера перечислены в `requirements.txt`. Они не устанавливают приложение или окно управления.

При необходимости создать изолированное окружение (Windows):

```powershell
py -3.11 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Для 2D-конвейера дополнительно установить Chromium в этом окружении:

```powershell
.venv/Scripts/python.exe -m playwright install chromium
```

Пути задаются переменными окружения:

| Переменная | Назначение |
| --- | --- |
| `BLENDER` | Исполняемый файл Blender |
| `FFPROBE` | Исполняемый файл ffprobe; FFmpeg также доступен через PATH |
| `DOTA_ROOT` | Корень установленной Dota 2 |
| `S2V` | Source2Viewer-CLI |
| `A8_RESOURCES` | Общие локальные ресурсы; по умолчанию `cache/resources` |
| `A8_WHISPER_MODEL` | Локальная модель распознавания для проверки реплик |

`tools/paths.py` ищет Blender и Dota в установленных библиотеках Steam. Новые зависимости агент подбирает по задаче, проверяя происхождение, лицензию, совместимость и стоимость. Обязательной локальной LLM нет: сценарий и постановку может подготовить сам агент. Имеющиеся CLI-планировщики — ограниченные вспомогательные инструменты, а не обязательный способ создания ролика.

#### Игровые ресурсы и голоса

Игровые модели, текстуры и звуки извлекаются из установленной Dota; для русских голосов нужна русская озвучка. Source2Viewer можно указать через `S2V` или разместить в `cache/resources/source2viewer/`. Упакованная сцена Blender с разрешёнными ресурсами может рендериться без установленной игры.

Общие извлечённые декорации хранятся в `cache/resources/sets/`; голосовые модели — в `cache/resources/voice/`. Например, необязательный `tools/skit/character_voice.py` ожидает в `voice/character/` runtime `bin/llama-tts.exe`, GGUF модели и projector. Закреплённые источники некоторых ранее использованных компонентов сохранены в [OPTIONAL_RESOURCES.json](docs/OPTIONAL_RESOURCES.json); их наличие не означает обязательную загрузку. Другой подходящий локальный голосовой инструмент допускается после проверки.

Не загружать модели ради ролика без озвучки. Узнаваемость голоса и разборчивость проверять отдельно. Запуск платных сервисов и расходы требуют согласия.

#### Работа и проверка

- Агент ставит движение в Blender скриптами и/или через интерфейс самого Blender; способ выбирает по результату.
- Фиксирует контактные позы, траектории, камеры и тайминг. Проверяет обе стороны рук и реквизита, начало и конец каждого действия.
- Запускает один GPU-рендер за раз. Сохраняет кадры и точные настройки для возобновления.
- Проверяет полный MP4: число кадров, FPS, звук, декодирование, движение и монтаж. Не заменяет просмотр отчётом тестов.
- Выдаёт скачиваемый MP4, местоположение редактируемой сцены и краткое состояние. Локальная ссылка сама по себе не гарантирует доступ с другого устройства.

Вспомогательные команды:

```powershell
py -3.11 tools/check.py
py -3.11 tools/blender/run_render_job.py путь/к/job.json
```

`tools/check_pipeline.py --out qa/pipeline-check` выполняет более тяжёлую интеграционную проверку 2D/3D, правок и возобновления. Запускать её при изменениях соответствующего конвейера и отдельно от активного GPU-рендера. Формат 2D-сцен описан в [PROJECT_GUIDE.md#scenes](#scenes).

#### Передача проекта другому агенту или компьютеру

При очистке отличайте рабочие инструменты и ресурсы от результатов проверок: `qa/`, `_fv_work/` и `__pycache__/` создаются заново, а `cache/resources/` содержит программы и модели, `_game/` — необходимые игровые данные. Не удаляйте весь `cache/` как временный каталог. В `out/` могут находиться единственные исходники и принятые ролики; сначала проверяйте их зависимости. Старые ветки с уникальными коммитами сохраняйте в проверенном Git bundle перед удалением ссылок, а уникальные незакоммиченные файлы — отдельно. Архивирование не освобождает место и не должно называться физическим удалением.

В Git хранить актуальные инструкции, код, параметры и список ресурсов с происхождением. Для продолжения конкретного ролика передать его `.blend`, аудио, скрипт сборки/`job.json` и нужные локальные ресурсы. Проверить доступность этих файлов на новом компьютере; пути с предыдущего ПК не считать доступными автоматически. Агент фиксирует выполненное, границы проверки и следующий шаг в `PROJECT_GUIDE.md#state`, существенные художественные замечания — в документации сцены.

#### Выводы постановки Баратрума

- Не подменять согласованный состав действующих лиц доступными моделями: здесь целями должны быть герои. До рендера сверять роли и каст с запросом. Начало должно содержать действие без задержки после замаха; проверять опору копыт по деформированным вершинам на реальном рельефе, включая переход к бегу.
- Не скрывать дальнее окружение ради ускорения, если это раскрывает границу карты. Проверять задник, весь край кадра и цвет вместе с референсом; успешная сборка и игровой цикл движения не делают постановку законченным видео.
- Корректные теги и матрица экспорта не исправляют художественно неудачную палитру. После замечания о цвете сравнивать исходные кадры нескольких планов: отдельно баланс нейтралей, зелень, лица/кожу, тени и светлые материалы. Фиксированная коррекция по всему монтажу должна улучшать эти отношения без автоматических скачков экспозиции; не считать прежнюю техническую проверку цвета одобрением пользователя.

- Игровая Charge уже содержит перемещение корня. При авторской мировой траектории сначала отделять продвижение от вертикальной работы тела, иначе герой движется дважды и выходит из кадра. Фазу шага согласовывать с расстоянием; проверять старт, циклический стык и торможение на непрерывной последовательности.
- Поворот корневого объекта на 90° не делает позу падения правильной: оси и исходный наклон корпуса различаются, а вытянутый меч, посох или конечность могут удерживать тело высоко над землёй. Проверять положение головы, таза и плеч, весь объём модели и реальную опору в конце. Допустимо использовать подходящую игровую позу покоя как конечную опору авторского движения; она не заменяет постановку импульса, реакции конечностей, полёта и контакта. Разные имена костей у melee/ranged проверять по фактическому ригу.
- Выбор устройства Cycles хранится также в настройках процесса, а не только в `.blend`. Перед серией выводить фактический активный GPU и измерять время через тот же вход рендера, которым будет рассчитана серия. Быстрая проба из процесса подготовки не подтверждает скорость отдельно запущенного рендера. Упаковку проверять через отсутствие внешних зависимостей; удалённые из рабочей копии объекты могут оставить неиспользуемые ссылки на библиотеки старой сцены.

##### Организация работы и границы доказательств

- Повторные заверения об исправлении шеи, маски и вардов оказались ненадёжны. Причина — узкая диагностика и поспешный переход к рендеру. - Проверки треугольных пересечений, IK, кадрирования и хешей полезны, но не доказывают естественность позы, читаемость зазора, юмор или эпичность. Значения из одной сцены не являются универсальными настройками для следующей.
- Полный монтаж смотреть при целевых FPS, отдельно — рискованные детали в исходном разрешении и размере телефона. Контрольные снимки во время воспроизведения не равны покадровой проверке. Честно фиксировать непроверенные аспекты.
- В EEVEE переход к 1080p выявил `Shadow buffer full`, которого не было на дешёвых пробах. Ёмкость увеличена с 512 до 1024 МБ, затронутый план пересчитан. Перед серией нужны широкие пробы при конечном разрешении и проверка VRAM/журнала; 96 сэмплов не исправляют нехватку теневого буфера.

- **Постановка и руки.** Численное совпадение с оружейной костью скрывало перекрученное запястье, хват пальцами и смещённую рукоятку. Решать всю цепь руки и поверхность контакта, отдельно ставить исходную позу; при накоплении компенсаций возвращаться к чистому ригу. Проверять обе стороны, одежду, выпуск и дальнейшее движение, а не только кульминационный кадр.
- **Темп и физика.** Глобальное замедление не исправляет спешку. Разделять смысловые контакты, сохранять естественную скорость усилия и перекрытие второстепенных движений. Вертолёт остаётся фоном, ускоряется при падении и заканчивает движение раньше ролика. Реакции зомби, опору и покой ставить под событие, не подменять универсальной игровой смертью.
- **Ключи Blender.** Старые дробные ключи давали рывки между целыми кадрами. В заменяемом интервале удалять их обратным проходом и проверять motion blur. Для оседания использовать согласованные quaternion и устойчивые опорные позы; ключевать позу до обновления dependency graph, иначе старое действие может восстановить прежние значения. Сначала проверять ясность действия и ответ партнёра, затем геометрию/контакты и свет, потом эффекты. #### Проверка вывода на анимационной пробе

Создан tools/blender/study_reference_reaction.py: контролируемое сравнение одновременного приветствия с отдельной ответной реакцией. Использует существующий локальный Rain rig и помощники проекта; новых моделей/зависимостей не загружалось. Rain: Blender Studio / Blender Foundation, CC BY 4.0. Камера, освещение, первый персонаж, продолжительность и качество одинаковы; изменено поведение второго персонажа. Это проверка читаемости взаимодействия, не перенос на риг Dota и не проверка речи.

Исходные контрольные позы записаны с шагом 6 кадров, между ними интерполяция; обе последовательности рассчитаны полностью по 180 кадров при 30 FPS, без разреживания итогового движения. Перед этим просмотрены 14 проб по 480×480. Полные варианты — 320×320; сравнение — 640×352, 6 с, без звука. Сцены и результат сохранены локально в out/reference-development/: simultaneous.blend, response.blend, acting-comparison.mp4, verification.json. Промежуточные кадры и манифесты — qa/reference-acting-probes-v3/. Исходный Rain сохранён по SHA-256. Два первых подготовительных запуска остановлены из-за избыточно дорогого вычисления рига; их неполные папки не являются результатом. Окончательный проход использует скрытие сеток только при записи контрольных поз, затем восстанавливает их для рендера.

**Фактический результат:** самостоятельный ответ лучше показывает инициативу и реакцию, чем одинаковые одновременные жесты. При этом проба выявила длинное удержание первого жеста (около 3,1 с), слишком нейтральное завершение и недостаточную крупность для тонкой мимики. Эти недостатки не считать устранёнными: эксперимент не принят как готовый клип или универсальный шаблон для роликов. Заимствовать принцип внимания и ответа, а тайминг, амплитуду и завершающее состояние ставить под конкретную сцену. Синхронные действия остаются допустимы, когда их требует замысел (например, E7).

Просмотр сравнения: 18 дискретных снимков за 11,076 с при зацикленном воспроизведении с исходной скоростью; исходный вариант дополнительно — 12 за 10,213 с. Декодирование MP4, 180 кадров и 30 FPS проверены; это не сертификация всех контактов сеток, тонкой деформации, субкадрового смаза или художественной готовности. Известный дефект исходного Rain-драйвера Spine3/STR-Spine4 не исправлялся и записан в отчёте. Никаких выводов об исправлении ригов Dota эта проба не даёт.

Для воспроизведения подготовить новую папку скриптом Blender --out NEW_FOLDER, затем выполнить tools/blender/run_render_job.py для каждого созданного simultaneous/job.json и response/job.json последовательно. Встроенный --render также считает полные кадры, но возобновляемый путь — сохранённые задания. Файлы модели Rain нужны локально; в Git хранится только исходник эксперимента.

Итог технической проверки изменений: 126 модульных тестов, tools/check.py 5/5, синтаксис новых Python-файлов и diff-check пройдены. Окна проверки и захват закрывать после просмотра. Визуальный разбор всей текущей подборки завершён в описанных границах; аудио не выдавать за проверенное. Принятые пользовательские ролики не переделывались.

#### Что меняется в подходе

1. **Сначала смысл кадра.** До модели и эффектов записать: что зритель понимает в начале, что меняется и какой кадр завершает ситуацию. В коротком меме вход должен сразу показывать значимый предмет, героя или условие шутки.
2. **Лицо и характер — часть постановки.** Для каждого героя задать направление внимания и эмоциональные состояния; согласовать глаза, брови, рот, голову, плечи и руки. Большая открытая челюсть сама по себе не заменяет реакцию. Не поддерживать одинаковую активность всей группы.
3. **Крупность отвечает задаче.** Общий план устанавливает ситуацию, средний показывает действие, крупный раскрывает реакцию или важный предмет. Это рабочий принцип, не обязательная одинаковая последовательность для всех видео. Каждый наезд, крен и склейка должны иметь причину.
4. **Движение включает подготовку и продолжение.** Смотреть позу до усилия, контакт, ускорение и последующую реакцию. Во время удержания плана сохранять взгляд, дыхание, перенос веса или движение аксессуаров, если они помогают состоянию героя. Не подменять живость постоянной тряской или движением всех частей тела.
5. **Окружение работает на кадр.** Распределять силуэты по глубине, отделять героя светом/тоном, избегать конфликтующего фона у лица и реквизита. В примерах заметны ясные световые акценты, цветовое разделение и выборочная глубина резкости. Ни тёмная картинка, ни высокий полигональный бюджет сами по себе не дают кинематографичности.
6. **Гротеск намеренный.** Увеличение масштаба, широкоугольное лицо и резкая вспышка допустимы как понятный акцент. Это не разрешение на вывернутые кисти, случайный смаз, зависание при падении или потерю контакта.
7. **Надпись дополняет действие.** В подборках часто одна короткая исходная фраза, белый текст с контуром и красное выделение ключевых слов. Для следующего ролика выбирать оформление по задаче, проверять телефонный размер и свободное место для лица; не делать этот стиль обязательным для любого жанра.
8. **Не копировать недостатки.** У референсов встречаются грубые формы, сильное размытие, пересвет вспышек и сжатие. Из этого нельзя выводить требование снизить качество наших моделей, света или деталей. Без исходников нельзя уверенно назвать использованный редактор, рендерер, риг или способ создания мимики.

#### Вывод по нашему ролику с миниганом

По сравнению с этими примерами в v14 внимание было преимущественно на выполнении действий и технических исправлениях. Следующим постановкам нужны более осмысленные крупные планы, различимые реакции героев, развитие их состояния и завершение события реакцией. Увеличение числа объектов, сэмплов или движений не решает это само по себе. Принятый v14 не переделывать без нового запроса.

#### Проверка перед следующим показом

- У первого кадра есть понятная задача; лишнее вступление отсутствует.
- Зритель понимает, на кого смотреть и почему меняется план.
- В ключевых моментах читаются глаза/лицо, контакт и последствие; текст их не закрывает.
- Движение проверено в рабочем темпе, реакция успевает прочитаться; отсутствуют случайные остановки и бессмысленная суета.
- Кадр работает в телефонном размере; свет, цвет и фон поддерживают главное действие.
- Звук проверяется отдельно при наличии реального доступа к аудио. Выводы о голосах и музыкальном ритме не выдаются за прослушивание по немым кадрам.

## Справочник формата 2D-сцен

### Сцены: любой ролик из JSON

Любой сегмент выпуска (`hook`, элемент `parts`, `outro`) может вместо готовой раскладки описать **сцену**: список элементов и таймлайн эффектов. Движок — `scene.js` + `scene.css`, анимация на GSAP (`vendor/gsap`, бесплатная лицензия GSAP). Рендер перематывает таймлайн сцены на время каждого кадра, поэтому кадры детерминированы.

```json
{ "voice": "…", "scene": { "bg": {…}, "cues": {…}, "items": […], "fx": […], "sounds": […], "camera": {…}, "cover": true } }
```

#### Настройки выпуска
| поле | значения |
|---|---|
| `transition` | `push` (сдвиг влево с размытием), `zoom` (наезд сквозь кадр), `flash` (вспышка). Без поля — переход темы. Стык режется прямо в движении, скорости совпадают |
| `subs` | `box` (белые плашки), `slam` (одно слово крупно), `line` (подчёркивание). Без поля — стиль темы |
| `theme` | как раньше: `k`, `c`, `b` … |
| `show_header` | `false` скрывает верхнюю подпись канала и полоску прогресса. По умолчанию шапка видна |
| `sapi_voice` | Имя установленного русского голоса Windows, например `"Pavel"`. Для субтитров нужна заранее загруженная модель Whisper small |

Пример немой анимации из текстового запроса сохранён в
`episodes/study_eclipse.json`. Для черновика включите
`FV_SILENT=1` и `FV_DRAFT=1` и передайте сценарий и путь MP4 в
`video.py`. Запрос записан в `_prompt`, а расположение объектов и
время движения задаются в `scene` теми же полями, что у других выпусков.

`episodes/study_spacing.json` показывает озвученный черновик с графикой
и субтитрами. Запустите его через `video.py` с `FV_DRAFT=1`. В этом
режиме голос синтезируется Windows, а тайминги распознаются локальной
моделью. При `FV_SILENT=1` проверяется раскладка с условными таймингами.

#### Время
`at` — число секунд от начала сегмента, **метка** из `cues` (`"afk"`) или метка со сдвигом (`"afk+0.3"`). Метка — слово из озвучки: `"cues": {"afk": "AFK"}`.

Для предпросмотра своего сценария и точечной правки без озвучки
используйте одинаковые настройки черновика через `quickstart.py`.
В первой команде задайте исходник, во второй — его изменённую копию.
Пример заменяет кадры 18–23 с частотой 15 FPS.

```powershell
py -3.11 tools/quickstart.py 2d --scene исходник.json --out qa/my-scene/base
py -3.11 tools/quickstart.py 2d --scene правка.json --frames 18:24 --out qa/my-scene/edit
```

В манифесте ревизии укажите `base/preview.mp4`,
`edit/insert.mp4` и `replace_at: 18`. Кадры за пределами интервала
и дорожка исходного MP4 сохраняются. Для правки, меняющей длительность
или содержание речи, эти команды подходят только для проверки картинки.

Короткий акцент на элементе одной сцены можно задать текстом.
В запросе укажите ID элемента и время в секундах. Сначала соберите
исходный предпросмотр, затем передайте запрос с `--plan-only`, чтобы
увидеть диапазон кадров. Для применения повторите команду без этого флага.

```powershell
py -3.11 tools/quickstart.py 2d --scene episodes/study_eclipse.json --out qa/eclipse-accent/base
py -3.11 tools/quickstart.py 2d --scene qa/eclipse-accent/base/source.json --base qa/eclipse-accent/base/preview.mp4 --request 'Подчеркни sun на 1,4 с' --out qa/eclipse-accent/edit --plan-only
```

В новой папке будут изменённый `scene.json`, `plan.json` с запросом
и диапазоном, `revision.json` и итоговый `revision.mp4`. Исходники
сохраняются в `base`, для отката откройте исходный `preview.mp4`.
Перед применением сверяются контрольные суммы сценария и исходного
видео. Поддержан один короткий акцент на элементе верхнего уровня
без пересечения с другим изменением его масштаба. Для произвольной
правки картинки используйте команды с `--frames` выше.

Чтобы продлить паузу между эффектами в одиночной сцене без озвучки,
звуков, движения камеры и встроенных анимированных медиа, задайте
величину прибавки и момент паузы в секундах.

```powershell
py -3.11 tools/quickstart.py 2d --scene qa/eclipse-accent/base/source.json --base qa/eclipse-accent/base/preview.mp4 --request 'Продли паузу на 1 с после 3,2 с' --out qa/eclipse-accent/long-hold --plan-only
```

Для применения уберите `--plan-only`. План записывает прежнее и новое
время сдвинутых эффектов. Если выбранный момент попадает внутрь эффекта,
команда попросит выбрать другое время. При изменении длительности
собирается полный черновик `edit/preview.mp4` в папке правки.

##### Монтаж и точечные правки

Сначала соберите и проверьте каждый план через `tools/quickstart.py`.
Общий монтаж выполняется агентом через FFmpeg; для экспортированных Blender-планов
есть `tools/blender/assemble_shots.py` (формат аргументов — `--help`).
Прежний `project_preview.py` удалён вместе с приложением: его формат проекта
и автоматическое изменение отдельного плана больше не являются рабочим интерфейсом.
Голосовой предпросмотр 2D доступен через `quickstart.py 2d --local-voice`;
для него нужны русский SAPI и локальная модель Whisper. Проверяйте дорожку отдельно
и в итоговом монтаже.

Для точечной правки картинки сохраните копию выпуска и отрисуйте только
нужный диапазон. Номера кадров отсчитываются с нуля в частоте итогового
видео, правая граница не включается. Для черновика 15 FPS оставьте
`FV_DRAFT=1`, для 30 FPS снимите эту настройку. Поддерживается локальная
разметка речи через `sapi_voice` либо исходник без речи с `FV_SILENT=1`.
При SAPI сохраните прежний голос и текст, чтобы положение субтитров и меток
не сдвинулось.

```powershell
$env:FV_DRAFT='1'
py -3.11 video.py --picture-range 111:122 edited.json qa/spacing-edit/insert.mp4
Remove-Item Env:FV_DRAFT
```

В проверке выпуска `study_spacing.json` к маркерам `linear` и `eased`
добавлен одинаковый эффект `pulse` с `at: "start+5.24"` и `to: 1.3`.
Оба акцента приходятся на общий финиш, исходная озвучка остаётся в полном
ролике. Укажите `insert.mp4` в поле `insert` манифеста ревизии
и задайте `replace_at: 111`.

Числа должны быть конечными; неизвестная метка или неверный сдвиг — ошибка,
а не запуск в нулевую секунду. Это относится также к `start`, `in.at` и звукам.

#### Элементы (`items`)
Общие поля: `id`, `type`, `x`, `y`, `w`, `h` (px в кадре 1080×1920), `z`, `rot`, `color`, `bg`, `radius`, `pad`, `border` (цвет рамки карточки), `tex`, `tint`, `frame`, `cls`, `in`.

Цвета — токены `acc ink red mint gold rad dire paper navy dark` или любой CSS.

| type | поля | что это |
|---|---|---|
| `text` | `text` (`|` перенос, `*акцент*`, `_маркер_`), `size`, `font` (`display`/`body`/`cap`), `align`, `acc`, `fit` | заголовок, подпись |
| `chip` | `text`, `size`, `fill` | плашка-ярлык |
| `stamp` | `text`, `size`, `color` | потёртый штамп |
| `number` | `value` (`35:00`, `9 200`, `4,5`) | крупная цифра; с `fx: count` набегает |
| `img` | `src`, `fit` (`cover`/`contain`), `pos` | картинка в рамке |
| `hero` | `src` | герой целиком, низом на нижний край рамки |
| `card` | `src`, `label`, `stamp`, `icon` (для иконок) | карточка героя/предмета |
| `anim` | `anim` (ключ из `assets/anim`) | анимированный герой |
| `shape` | `kind` (`arrow`/`line`/`bracket`/`zig`), `stroke`, `color` | рисованный интерфейс |
| `row` / `col` | `items`, `gap`, `child` (общие поля детей) | ряд/колонка, делит место поровну |
| `panel` | `items` (координаты внутри панели) | контейнер с текстурой |
| `video` | `src` (`file:…mp4`), `from`, `dur`, `audio` (громкость звука клипа, 0 — без звука), `start`, `loop`, `hold` (`false` — виден только пока идёт) | клип из игры в рамке; кадры нарезаются под размер элемента |
| `model` | `hero` (ключ, напр. `juggernaut`), `anim` (имя анимации), `parts` (`all` или список), `yaw` (°), `zoom`, `tilt`, `fov`, `rim` (цвет контрового света), `key`/`ambient` (яркость), `speed`, `start`, `in_place` | 3D-герой из файлов игры с одеждой и оружием, анимация по времени сцены |
| `lottie` | `src` (`file:assets/lottie/….json`), `start`, `speed`, `loop`, `fit` (`cover`) | готовая анимация Lottie (например, с lottiefiles.com, бесплатные — формат Lottie JSON) |

**Мем** — `{"type": "meme", "name": "хэнк_понял", "x": 90, "y": 560, "w": 840, "h": 620, "in": {"fx": "pop", "at": "понял"}}`: кусок клипа вокруг лучшего момента (пик движения и громкости) со звуком, 1,6 с, виден только пока идёт (`dur`, `lead` — сколько до пика, `from` — свой старт, `hold: true` — оставить последний кадр). Каталог — `py -3.11 tools/memes.py` (`_game/memes/catalog.json` и лист `memes.jpg`); если автоматический момент мимо сути, точное время — в `_game/memes/peaks.json` (`{"хэнк_понял": 6.2}`), пересборку каталога оно переживает. Любой клип — тем же `video` с `src`. Чёрные поля клипа срезаются сами. Файлы мемов лежат локально в `_game/memes/` (не коммитятся), поэтому такой ролик рендерится локально.

`src`: `hero:juggernaut`, `item:blink`, `ability:kunkka_torrent`, `file:assets/…`, `game:panorama/images/minimap/dotamap.png` (картинки из файлов игры).

Для `video` начало выбирается по первому заданному значению:
`start` → `in.at` → `at` → `0`. Ноль — заданное время, `null` — пропуск.
`loop:true` повторяет изображение и звук до конца сегмента; `hold:false`
скрывает клип до старта и после окончания неповторяемого клипа. `hold:true`
оставляет крайние кадры, но не продлевает звук. При отрицательном старте
в начале сегмента используется соответствующая фаза клипа. Период равен
числу извлечённых кадров / fps: длинный WAV обрезается, короткий дополняется
тишиной. Звук клипа не переходит в соседний сегмент.

`child` в `row`, `col` и `panel` задаёт неглубокие defaults: поля отдельного
ребёнка заменяют одноимённые общие поля целиком. Они применяются до загрузки
медиа, поэтому наследуемые `src`, размеры, `audio`, `start`, `loop` и `hold`
учитываются при подготовке и при сведении одинаково.

#### Ресурсы из файлов игры (3D, миникарта, иконки)
Файлы игры хранятся локально в `_game/` и не публикуются в Git.
Экспортировать модели и текстуры следует установленным Source2Viewer CLI;
настройка путей описана в [SETUP.md](#setup). Старые обёртки
`vpk_tool.py`, `dota_export.py` и `map_crop.mjs` в текущий проект не входят.
Для 2D/Three.js героев нужны GLB в `_game/models/<герой>/`, для карты —
GLB и соответствующие текстуры. Для Blender есть `tools/blender/dota_map.py`.
Проверяйте экспорт, материалы, масштаб и совместимость анимаций до рендера.

#### 3D-площадка (`stage`)
`{ "type": "stage", "map": "river", "actors": [{ "hero", "anim", "x", "y", "z", "yaw", "phase", "speed", "scale", "splash" }], "cam": { "pos", "look", "to": { "pos", "look" } }, "fov", "sky", "sky_top", "fog_near", "fog_far", "water": { "color", "deep", "opacity" } }` — герои в настоящей карте: террейн смешивается из 4 слоёв как в игре (dota_map.js), вода своя под цвет дотовской, небо — градиент. Без `map` — простая река своей отрисовки. `ambience: "river"` в сцене — шум воды.

Дети контейнера получают id `родитель.0`, `родитель.1` … (если своего нет).
Все id, включая вложенные и унаследованные через `child`, должны быть уникальны
в пределах сцены. `stage.sun_dir` — ненулевой вектор из трёх конечных чисел:
он задаёт одно направление солнца для героев и многослойного материала карты.
По умолчанию `[6, 10, 6]` (координаты Three.js, Y вверх).

**Текстуры** `tex` — фото (Poly Haven, CC0): тёмные `wood oldwood doors metal plate stone blocks rock cliff leather forest`, светлые (тёмный текст) `planks rust cobble burlap concrete plaster`; бумага `paper parchment`; рисованные `noise grid scan halftone`. У всех фото-текстур фаска и затемнение; `tint` — свой оттенок поверх (например `["rgba(10,35,64,.5)", "rgba(10,35,64,.8)"]`). Новые текстуры — assets.yml, поле `textures`, список ключей: `?wood`, `?metal`, `?rock`.
**Рамки** `frame` (можно списком): `plate corners rivets tape ticket cap`. `tape` не сочетается с `corners`/`rivets`.
**Фон сцены** `bg`: `{"grad": [...]}`, `{"color": …}`, `{"tex": "grid"}`.

#### Появление (`in`)
Строка или `{ "fx", "at", "dur", "stagger", "dist" }`:
`fade rise drop pop slam left right wipe iris stamp draw` (для `shape`), для текста — `lines` (строки из-под маски), `chars` (по буквам), `type` (печать).

**Первый кадр ролика собран:** в первом сегменте всё, что появляется в первые 0,6 с, сразу стоит на месте (превью в ленте). Выключить — `"cover": false`.

#### Эффекты (`fx`)
`{ "target", "fx", "at", … }`. Цель: `"id"`, `"id.*"` (все дети), `"id em"` (CSS внутри), `"@all"` (вся сцена).

| fx | параметры | что делает |
|---|---|---|
| любое из `in` | | появление по метке |
| `pulse` | `to` | короткий удар масштабом |
| `shake` | `dur` | тряска |
| `jump` | `dist` | буквы акцента подпрыгивают волной |
| `gray` / `color` | | обесцветить / вернуть цвет |
| `dim` / `show` / `hide` / `out` | `to` | приглушить, показать, скрыть, увести вверх |
| `move` | `x y scale rot ease` | сдвиг |
| `mark` | | маркер под `_словом_` |
| `stamps` | | штампы на карточках (`stamp` у `card`) |
| `count` | `dur ease` | число набегает от 0 |
| `swap` | `text` | смена текста переворотом |

#### Камера
По умолчанию медленный наезд 1 → 1,03 за сегмент. `"camera": {"from": 1, "to": 1.06, "x": 0, "y": -40}` или `false`.

#### Звуки (`sounds`)
Синтезированные, тише голоса: `{ "kind": "stamp|bubble|tick|pop|whoosh", "at": "метка+0.2", "gain": 1 }`.

#### Проверка описания
Перед озвучкой проверяются типы, текстуры, рамки, эффекты, звуки, цели,
уникальность id и объявление меток. Ошибки печатаются строками `⚠` и останавливают
сборку. После озвучки повторно проверяется разрешённое время: ненайденное слово
также останавливает сборку. Это проверка описания, не художественная приёмка.

Сценарии считаются доверенным локальным кодом: текст допускает HTML,
`file:` обращается к локальным ресурсам, браузер имеет расширенный доступ
для рендера. Не запускать непроверенный чужой JSON как изолированный документ.
Проверки выше не являются защитной средой для недоверенного импорта.

#### Что ещё делает рендер
- Обложка: первый кадр сохраняется как `cover_NNN.png` рядом с роликом (и публикуется в ветку renders).
- Громкость выравнивается к −14 LUFS (стандарт TikTok/Shorts).
